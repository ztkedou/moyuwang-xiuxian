## 🚀 一键部署

不想配环境？用 Docker 三条命令，把整套（前端 + 服务端 + 数据库）跑在自己的机器或服务器上：

```bash
cp .env.example .env          # ① 生成配置（记得填一个 GM_PASSWORD）
docker compose up -d --build  # ② 构建镜像并启动
# ③ 浏览器打开 http://localhost:8080/
```

装过 `make` 的话更省事：`make init && make up`。

- **完全不懂 Docker？** 看 **[docs/DEPLOY-QUICKSTART.md](./docs/DEPLOY-QUICKSTART.md)** —— 从装 Docker 到改端口、升级版本、常见报错，一步步都有。
- **没装 Docker？** 只要 Node.js 22+，`./deploy.sh` 一样能起（纯 Node 网关，**不需要 nginx**）。
- 数据库挂在 Docker 卷里，`docker compose down` 不会丢档；密钥只从 `.env` / 环境变量注入，**镜像里不含任何密钥**。

> 想自己改代码、重跑装配，或部署到自建 Nginx + systemd 上，见下方「[本地运行 / 构建 / 部署](#-本地运行--构建--部署)」。

## 📖 这是什么

《摸鱼修仙传》是一款**文字向放置修仙游戏**：你在摸鱼时挂机打坐、历练闯荡，逐步从炼气一路突破到更高境界，
途中经营洞府灵田、结交道友、加入仙盟、拜师收徒、参与限时活动。

本仓库是这个游戏的**完整可复现源码包**——包含前端补丁管线、服务端（单文件 TypeScript，含 200+ 接口）、
构建脚本、数值与设计文档。**任何人 clone 后都能重建出与仓库内参考产物逐字节一致的产物**（产物 md5 可校验）。

### 技术栈

| 层 | 技术 |
|---|---|
| 客户端 | React 19 + TypeScript 5.8 + Vite 6（上游基座构建，本仓库以「冻结基座 + 补丁管线」方式改造） |
| 服务端 | Node.js + Express + TypeScript 单文件（`srv/index_v28.ts`），SQLite 持久化 |
| 构建/装配 | Python 3 脚本（`build_v26n.py` / `localtest/chain_build.py`） |
| 部署 | Nginx 静态托管 + systemd 常驻服务 |

## 🧩 仓库结构与「冻结基座 + 补丁管线」开发模型

> ⚠️ **重要说明**：本改版的前端是在上游源码基础上做了**源码级改造**，而那份改造后的源码树已不可得。
> 因此本仓库**不是**「上游源码 + 改动内联」的形式，而是诚实的 **「冻结基座 + 补丁管线」** 形式：
> 以一份**不可变的冻结 bundle** 为基座，用脚本按固定顺序**注入**我们的全部改造，最终产出与线上**逐字节一致**的产物。

```

├── yl_patch.py                   # 补丁引擎（锚点定位 + 字符串注入）
├── patches/
│   ├── client/yl_*_ext.py      # 135 个客户端补丁模块（每个对应一批玩法改造）
│   └── server/srv_patch_*.py   # 78 个服务端补丁模块（SRV_CHAIN 64 环串行应用）
├── build/
│   ├── index.html                # 页面外壳（引用最终 bundle）
│   └── assets/
│       ├── index-v26m-20260927.js    # ★ 前端冻结基座（不可变，装配输入）
│       ├── index-v2913-20261002.js  # ★ 装配产出（= 0.9.13 产物，可 md5 校验）

│   ├── game-dicts.json           # 游戏数据字典（物品/功法/事件…）
│   └── *.sql                     # 数据库建表/迁移脚本

│   ├── chain_build.py            # ★ 服务端链式装配器（64 环串行应用 srv_patch_*）
```

### 复现线上产物

```bash
# 1) 重建前端 bundle（冻结基座 → index-v2913-20261002.js）
python build_v26n.py

# 2) 重建服务端（冻结基座 → 串行应用 64 环补丁 → srv/index_v28.ts）
python localtest/chain_build.py --srv

# 3) 校验基座指纹（不改任何文件，只对 md5）
python localtest/chain_build.py --check
```

> 依赖：Python 3.10+、Node.js 22+（`chain_build.py` 里的 `NODE` 常量请按本机路径调整）。

| 服务端冻结基座（装配**输入**） | `_v281_base/index_v28.base.ts` | `f6ecc82e72d8425d5064f765d7de0684` |
| 游戏数据字典（全链不变） | `srv/game-dicts.json` | `1b635513f553875060869272b790f910` |

> **只保留最新一版定版产物**：仓库内只入库上表这份 **0.9.13 定版**。
> 更早版本（0.8.11 / 0.8.11.1 / 0.9.0 等）的产物**均未入库**，此处不再逐一登记 md5，
> 它们对应的更新日志见 [CHANGELOG.md](./CHANGELOG.md)。
> 注意：每次发版都会**整包更换产物文件名**（版本段随版本走），所以「同一份产物在不同目录里叫不同的名字」是正常的。

> ## ⚠️ 「同名文件 md5 不同」是正常的 —— 别把它当校验失败
>
> **`b4586dba…` 是本仓库内这份 0.9.13 定版快照的 md5，也是本仓库唯一的校验基准。**
>
> 但你可能在其他地方（例如某个部署工作区 / 本地构建目录）看到**同样叫 `index-v2913-20261002.js`
> 却 md5 不同的文件**。这**不是**仓库里的产物出错，而是：
>
> | 文件位置 | 是什么 |
> |---|---|
> | **本仓库** `build/assets/index-v2913-20261002.js` | **0.9.13 定版快照**（md5 `b4586dba…`）—— 只读参考物，「可复现」承诺的比对基准 |
> | 某个部署工作区 / 构建目录下的同名文件 | 该文件**已被后续构建就地覆写**，内容是迭代中的中间态，**不是定版产物** |
>
> **判断标准只有一条：以本仓库内的文件为准。** 仓库内这份是冻结的、不会再变；
> 一旦你在别的目录里跑过 `build_v26n.py`，那个目录里的同名文件就已经**不再是**定版产物了
> （原因见下面「构建会覆盖产物」）。
>
> 同理，`index-v26m-20260927.js`（`b315eb1a…`）与 `_v281_base/index_v28.base.ts`（`f6ecc82e…`）
> 是**装配输入**（冻结基座），而 `index-v2913-20261002.js`（`b4586dba…`）与 `srv/index_v28.ts`
> （`77c705ec…`）是**装配产出** —— 两者角色不同，不要混为一谈。

## 🚀 本地运行 / 构建 / 部署

### 本地运行（开发体验）

```bash
# 1) 准备环境变量
cp .env.example .env
#    编辑 .env，至少填 JWT_SECRET 与 GM_PASSWORD

# 2) 启动服务端（提供 /api/* 接口 + 静态托管 build/）
#    需要 Node.js 22+；服务端是单文件 TS，可用 node --experimental-strip-types 直接跑
node --experimental-strip-types srv/index_v28.ts

# 3) 浏览器打开
#    http://localhost:3000/            （前端）
#    http://localhost:3000/api/...     （接口）
```

> 前端是**构建产物**（`build/` 目录），无需 `npm install` 即可静态托管。
> 若只想看前端：任意静态服务器指向 `build/` 即可（注意 `index.html` 引用 `./assets/` 相对路径）。

### 重建前端 / 服务端

见上一节「复现线上产物」。产物可直接用于部署。

> ## ⚠️ 构建会覆盖产物 —— 跑之前先备份
>
> **本仓库的装配脚本是「就地覆写」式的，不产生带 `.new` 后缀的新文件，也没有二次确认。**
>
> | 脚本 | 会覆写 | 后果 |
> |---|---|---|
> | `python build_v26n.py` | `build/assets/index-v2913-20261002.js`（**0.9.13 定版产物**）与 `build/index.html` | 覆盖后该文件的 md5 不再等于定版产物指纹，`docs/PUBLISH-MANIFEST.md` 里的参考 md5 立即失效 |
> | `python localtest/chain_build.py --srv` | `srv/index_v28.ts`（**服务端全链定版产物**） | 同上；若该文件曾被手工改动而未回流到补丁模块，改动**永久丢失** |
>
> **因此，跑任何一个装配脚本之前：**
>
> ```bash
> # 1) 先备份两份定版产物（这是唯一的回滚点）
> cp build/assets/index-v2913-20261002.js build/assets/index-v2913-20261002.js.bak
> cp srv/index_v28.ts                      srv/index_v28.ts.bak
>
> # 2) 记下当前 md5 留档，跑完后比对是否与预期一致
> md5sum build/assets/index-v2913-20261002.js srv/index_v28.ts
>
> # 3) 现在才跑装配
> python build_v26n.py
> python localtest/chain_build.py --srv
> ```
>
> **另外两点必须确认：**
>
> 1. **`build/assets/index-v2913-20261002.js` 是「定版产物」，不是可随意重生成的中间物。**
>    它是本仓库「可复现」承诺的**校验基准**（md5 `b4586dba4943bf62cc4ca818af31fb66`）。
>    一旦被覆盖，除非你手上还留着原文件，否则**这份基准就永久丢失了** —— 备份是唯一保险。
> 2. **`srv/index_v28.ts` 必须是「冻结基座 + 全链补丁」的可重建物，不能是手工改过的孤本。**
>    如果线上某次热修是直接编辑该文件而未回写到 `srv_patch_*.py`，那么重跑 `chain_build.py --srv`
>    就会**静默抹掉那次热修**（脚本不会报错，产物 md5 却会变）。改服务端请一律改补丁模块，
>    不要直接改 `srv/index_v28.ts`。
>
> 备份文件（`*.bak`）已在 `.gitignore` 中忽略，不会误入库。

### 部署（自建服务器）

参考 [docs/DEPLOYMENT.md](./docs/DEPLOYMENT.md)：Nginx 静态托管 `build/` + systemd 常驻 `srv/index_v28.ts`，
环境变量通过 `.env` 注入。**本仓库不含任何真实服务器地址或密钥**，请自行填写。

> ## ⚠️ 部署前必须设置 `GM_PASSWORD` 环境变量（否则服务无法启动）
>
> 自 **0.8.9** 起，服务端**已移除**早先的弱口令兜底默认值（`process.env.GM_PASSWORD || 'gamer'`）。
> 现在 `srv/index_v28.ts` 的行为是：**未设置 `GM_PASSWORD` 就直接以 `[FATAL]` 拒绝启动**，
> 而不是退化成一个可猜的口令。
>
> ```ts
> const GM_PASSWORD = process.env.GM_PASSWORD;
> if (!GM_PASSWORD) {
>   console.error('[FATAL] GM_PASSWORD 未设置，拒绝以弱口令启动。请在 .env 配置 GM_PASSWORD 后重启。');
>   // …随后进程退出
> }
> ```
>
> 因此部署前**必须**在 `.env` 中显式设置一个强口令，否则服务起不来：
>
> ```dotenv
> GM_PASSWORD=<请改成你自己的强口令>
> ```
>
> > 注：本仓库的**冻结基座** `_v281_base/index_v28.base.ts` 中仍保留旧写法
> > `process.env.GM_PASSWORD || 'gamer'` —— 那是历史基座的原貌；
> > 装配链里的 `srv_patch_baseclean089.py` 会把它移除，最终产物 `srv/index_v28.ts` 中已无 `'gamer'`。
>
> 同理，`JWT_SECRET` 也请务必显式设置（未设置时服务端会生成随机密钥并写入 `.jwt_secret`，
> 重启/迁移时容易导致全员掉线）。
