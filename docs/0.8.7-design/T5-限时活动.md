## 2. 统一框架决策（九条，全部活动共用）

1. **活动实例仍走 `events` 表**：每期一行，GM 既有接口建场（窗口/enabled/全服播报零改动）。新增 4 个 type：`rank_battle` / `checkin_fest` / `token_shop` / `boss_raid`，**target 一律 `'live'`**（`stones2_live` 先例），永不进倍率引擎。
2. **玩法状态放列不放 JSON**：新状态表全部以 `(player_id/event_id[, date/day])` 建主键，主键=幂等与并发防重的唯一防线（`activity_rain_state` :885-898、`fun_daily` :774 同款纪律）。
3. **结算器**：并列于 `rainSettleTick`（:6268-6354）新增 `actSettleTick`（冲榜结算 + 妖兽到期结算），同款纪律——内存重入保护（:6269 先例）、`engine_on` 内存镜像**首行早退**（:6348-6349 先例）、`.unref()`、启动镜像 `engine_on`（:6355-6358 先例）；**另须开机立即跑一轮**——现网灵雨没有 boot-run（:6355-6358 只做内存镜像），但冲榜/妖兽的「窗口结束结算」不能赌下一次定时 tick：停服跨过窗口末端时，重启后必须补结算，幂等由快照表主键兜底。单进程假设与灵雨相同（落地方案 §7.2.5）。
4. **日切口径**：玩法「每日」一律 `utcDateStr()`（:6686，与 fun_daily/worldboss/activity_frame 现网主口径一致，玩家只感知一个日切时刻）；冲榜窗口聚合按 `stats_daily` 的 `bjDate` 键（:4867）换算区间。
5. **kill switch 双层**：`activity_config.engine_on` 全局 + `events.enabled` 逐场。所有新端点与结算器都必须尊重两层——层 1 关：活动接口返回但玩法端点 409；层 2 关：该期不结算不发奖。
6. **业务拒绝一律 400/409**（`Xc()` 把 403 当会话失效强制登出，0.8.5 铁律）。登录失效 401 除外（框架既有）。
7. **扣费纪律三段式**：先占次数/库存位（UNIQUE 或守卫式单语句）→ 再扣灵石 → 失败补偿删行/回滚（fun_daily :7742-7759 先例）；余额扣减用守卫式 `UPDATE … SET balance=balance-? WHERE … AND balance>=?`，`changes=0` 即 409。
8. **EV 红线**：每个涉及支付或产出的点给出 EV 不等式，写入 §8 汇总表；数值定值时**不等式是装配门禁的一部分**（断言进 dryrun）。所有赔率类常量不新增——「加大」只动注额与次数。
9. **客户端一个容器**：现有「限时活动」只读面板（`YlxwTEvents`，bundle @801006，0.8.6 落地方案 §5）升级为 tab 容器「活动中心」：总览（现列表）+ 冲榜 + 签到 + 灵玉阁 + 万妖巢穴，复用 F6 的 `YlxwFuse` 两列融合壳（`grid grid-cols-1 md:grid-cols-2`）。**零改动兜底**：不做容器时，4 个新 type 在只读列表照常显示（typeName 回退先例），玩法入口可后置补。

## 3. 活动 A：仙途冲榜（`rank_battle`，P0，难度 中）

> 原策划案方案二落地版。窗口期 7 天，双榜（灵石获取榜 / 击杀榜），数据源 `stats_daily` 窗口聚合，服务端结算发邮件。

| 项 | 设计 |
|---|---|
| 定位与周期 | 每期 **7 天**（GM 建场定窗口，建议周一 00:00 → 下周一 00:00 北京时间）；每期一个 `events` 行（type=`rank_battle`） |
| 参与条件 | 已建角色（有 `saves` 行）即自动入榜候选；**有效参与线**：窗口内 `SUM(minutes) ≥ 60 分钟`（定档，验算见《数值表-T5T6》§2.1），低于线只显示不计奖 |
| 玩法循环 | 被动参与：窗口内正常游玩，`stats_daily.silver_gain / kills` 按日累计（服务端埋点 :2044，灵石增量受经济钳制）。主动操作仅「查榜」：活动中心实时榜 TOP50 + 自己的排名/分差 |
| 每日限次 | 无玩法次数；**每日一次榜单快照**（结算器 tick 每日缓存一次 TOP50 到内存/表，防高频聚合查询；聚合列须加索引 `idx_stats_daily_date(date)`） |
| 奖励框架 | 双榜各自独立计奖，**一律按境界时薪折算**（`rainHourlyStones` 同源公式，:4630-4646 先例）：每榜第 1 名 = 时薪 × 12 h；第 2~3 名 = × 8 h；第 4~10 名 = × 5 h；第 11 名~前 30% = × 2 h；有效参与 = × 0.5 h（全部定档，验算见《数值表-T5T6》§2.1）。双榜同得者叠加。发放走 `insertMail(…, {noChronicle:true})`（灵雨先例：自动例行收益不入江湖志，落地方案 §8.3） |
| 结束与刷新 | 窗口结束后的首个结算 tick：聚合 → 写快照表 → 逐人发邮件 → 榜首一条 chronicle 全服公告（`【活动】` 前缀，:6226 先例）。快照落表后该期冻结，重复结算被快照表主键挡死。下期新 event_id，成绩不跨期 |
| EV 与防刷 | 无投注、无购买。投放上限 = 参与人数 × 单人所得封顶（两榜合计 ≤ 时薪 × 24 h（= 榜 1 双榜恰满，A1 验算））。防刷四层：① `silver_gain` 来自 `/api/save` 存档差值且受 `settleSaveEconV2` 正增量钳制；② `minutes` 伪造面沿用灵雨墙钟封顶结论（仅用于参与线，不影响名次）；③ 同账号多角色天然按 user_id 分列不合并；④ 结算只认快照表，窗口结束后的迟到存档不计入 |
| 新表 | `activity_rank_settled(event_id INTEGER, board TEXT, user_id INTEGER, rank INTEGER, tier TEXT, score INTEGER, reward INTEGER, settled_at INTEGER, PRIMARY KEY(event_id, board, user_id))` —— 结算快照 + 幂等守卫（主键含 user_id：参与档无排名也要落表；重结算被 PK 挡死）；可选索引 `idx_stats_daily_date ON stats_daily(date)` |
| 新 API | `GET /api/activity/rank?eventId=&board=silver|kills` —— 活跃期实时聚合（LIMIT 50 + mine）；已结算期返回快照。频控 60/min，`authenticateToken` |
| 客户端改动 | 活动中心「冲榜」tab：双榜切换、TOP50、我的名次卡片、结算倒计时 |
| 验收要点 | ① 建场后 `/api/events` 出现新行且 `typeName='仙途冲榜'`；② 造 3 个测试号不同 silver_gain → 榜序正确、参与线以下不计奖；③ 窗口结束后首个 tick 结算：`activity_rank_settled` 行数=两榜发奖人数之和，**二次触发零新增**（幂等）；④ 邮件可领、`chronicle` 恰 +1（独有信号 `【活动】`+场次名）；⑤ `engine_on='0'` 时 tick 首查询早退零写入（对齐灵雨验收手法）；⑥ 境界缩放：ylt_new/ylt_mid/ylt_max 同名次所得严格等于各自时薪档 |

## 4. 活动 B：仙缘七日礼（`checkin_fest`，P0，难度 低）

> 原策划案方案三落地版。与一次性 `week_goals`（:8090，仅首周）互补的**可重复排期**节庆签到。每期 7 天，断签不补。

| 项 | 设计 |
|---|---|
| 定位与周期 | 每期 **7 天**（`events` 行 type=`checkin_fest`）；建议配合节日/版本节点排期，每月至多一期 |
| 参与条件 | 已建角色；窗口内任意一天登录即可「从当天开始签」（第 1 天错过则从当天对应天签，前期天数作废） |
| 玩法循环 | 每日打开活动中心 → 签到页 → 点「领取今日仙缘」。天序 = `clamp(1, 7, floor((now − start_at)/86400000) + 1)`（与 events 倒计时同一时钟） |
| 每日限次 | 每玩家每期每日 **1 次**（`activity_checkin` 主键 `(player_id, event_id, day)` 兜底；`INSERT OR IGNORE` → `changes=0` → 409「今日已签」，:8083-8084 先例） |
| 奖励框架 | 第 N 天 = 境界时薪 × N/6 h；第 7 天 = 时薪 × 3 h；**全勤奖**（领取第 7 天时 `COUNT(*)=7` 校验）额外 = 时薪 × 3 h（全部定档：全勤合计 9.5h，验算见《数值表-T5T6》§2.2）。发放 = `updatePlayerSave` 直入账（:8103 `week/claim` 先例，不走邮件、不触发鸿函、零邮件量） |
| 结束与刷新 | 期结束未领的天数**作废不补发**；下期新 event_id 重新 7 天。断签设计：**v1 不做补签**——补签若定价低于当日奖励折算值即构成 EV>1 的正回报购买，为守住红线直接砍掉（见 §8-B1） |
| EV 与防刷 | 免费投放，无支付即无赌性 EV；总投放公示 = 全勤合计 ≈ 时薪 × 9.5 h（= Σ(N/6)+3+3；原《限时活动策划方案》「≈7h」为口算误，已勘误）。防重复靠主键；防「未到期领取」服务端重算 day 校验（不信任客户端传参） |
| 新表 | `activity_checkin(player_id INTEGER, event_id INTEGER, day INTEGER, claimed_at INTEGER, PRIMARY KEY(player_id, event_id, day))` |
| 新 API | `GET /api/activity/checkin?eventId=` —— 7 天档位/已签历史/今日可签；`POST /api/activity/checkin/claim {eventId}` —— 直发 |
| 客户端改动 | 活动中心「签到」tab：7 格日历（已领/可领/作废三态）+ 全勤进度条 |
| 验收要点 | ① 并发 6 发 claim 恰 1 成功、5×409（并发反向对照铁律）；② 服务端改系统时钟跨天后可再领（day 推进），同日重领 409；③ 第 7 天领取时不足 7 行 → 无全勤奖，恰 7 行 → 含全勤奖；④ 窗口外 claim → 409「活动未开启/已结束」；⑤ 直入账断言：`player.spiritStones` 增量 == 档位值（不走 mail 表，`mail` 行数不变） |

## 5. 活动 C：灵玉阁（`token_shop`，P1，难度 中）

> 原策划案方案四落地版。14 天一期：活动期在**服务端结算点**掉落代币「灵玉」，活动商店固定率兑换。玉可跨期囤积。

| 项 | 设计 |
|---|---|
| 定位与周期 | 每期 **14 天**（`events` 行 type=`token_shop`）；建议双月常驻 |
| 参与条件 | 已建角色；窗口内产生服务端结算收益即自动掉玉 |
| 玩法循环 | 游玩 → 服务端结算点掉玉 → 活动中心「灵玉阁」查看余额 → 商店兑换。**掉玉只挂 3 个服务端入账点**（`actApplyGain` 真正入账的行，均已有 `resolveEventMults` + `resolveMentorGains` 挂点先例）：炼丹出炉领取（:5662）、灵田收获（:5813）、离线收益领取（:8333-8334）。**离线预览接口（:8270-8271）不挂**——预览与领取各有一份 actApplyGain，挂预览必然双计。**在线打坐/历练结算在客户端混淆码内，一律不挂**（客户端上报不可信，落地方案 §2.1 已论证） |
| 每日限次 | 掉玉日上限 300 玉/日（≙ 150 万灵石结算量），记账表 `activity_token_daily` 主键 `(player_id, date)` 守卫；单期不掉上限（余额可囤）。商店购买次数：灵石袋类每期限购 小 20 / 中 10 / 大 5 次（防跨期倾销），称号/装饰类限 1 次 |
| 奖励框架 | 商店 = **服务端常量字典 `ACT_SHOP_ITEMS`**（免表，最少表原则）。商品三类：① 灵石袋 小/中/大 = 100/300/800 玉 → 时薪 × 1/4/12 h（按领取时境界发放）；② 限时称号 2500 玉（`grantTitleBySource` :8104 先例发放，活动限定 source）；③ 装饰/外观 1500 玉。**兑换率恒定无随机**（全部定档，验算见《数值表-T5T6》§2.3） |
| 结束与刷新 | 窗口结束商店关闭（兑换端点 409「本期灵玉阁已闭阁」）；**余额跨期保留**（`activity_token` 不按期清零），下期继续用。期次只控制「掉玉与商店开关」 |
| EV 与防刷 | 闭环不等式（§8-C1，定值 r=2）：掉玉率 2 玉/万灵石结算 × 灵石袋折算 v 灵石/玉 ≤ 9000（最贵大袋 v_max=3446.8@长生 ⇒ 2×3446.8=6893.6；即玩家把结算产出全换成玉再换回来，至多拿回 68.9%）⇒ **全闭环 EV ≤ 0.689 < 1**，挂机越多亏得越少但永不回本，纯留存向。防刷：玉只在服务端结算点产生（伪造存档不产玉）；日上限；不可交易（无任何转移 API）；兑换守卫式单语句防并发透支 |
| 新表 | `activity_token(player_id INTEGER, token_key TEXT, balance INTEGER, earned_total INTEGER, spent_total INTEGER, updated_at DATETIME, PRIMARY KEY(player_id, token_key))`；`activity_token_daily(player_id INTEGER, date TEXT, earned INTEGER, PRIMARY KEY(player_id, date))` |
