### 1.4 结论：**服务端改造 + 客户端面板重做 + 原生不动**

1. **服务端 = 改造**：V27 表结构与守卫式写法完全符合本项目纪律（部分唯一索引/单语句 INSERT/先扣款后补偿），推倒重做只会丢掉这些已验证的防线。缺的是状态码合规（G1）、检索（G2）、申请审批（G3/G4）、捐献回馈（G6）、硬化（G7）。
2. **客户端 = 重做面板**：`YlxwTSect` 是极简单块（创建/加入/捐献/领奖四件事），按 T7 目标重写为完整仙盟面板，以新模块**覆盖注册** `YLXW_COMP.sect`（先例：tower/expedition/reforge/spell/payout 全是模块后挂注册，bundle @962974/@1016340）。旧函数体保留不删（死代码无害，删除徒增断言面）。
3. **原生宗门 = 不动**：其四页签是上游内容 + Y22 功法阁服务端权威表已自洽；打通存档镜像（写 `player.sectId`）会引入 gm_revision 冲突面，收益不成比例。唯一互通点 = G6 的捐献回馈贡献（服务端写存档，走 `updatePlayerSave` 既有安全通道）。

## 2. 统一设计决策（九条）

1. **业务拒绝一律 400/409，绝不用 403**（`Xc()` 403 强制登出，铁律①）。§6.1 列出全部 **13 处**改码点（2026-09-29 复核定数；草稿初版记 14 处，其中 :9845 经复核已是 400，见 §6.1）；登录失效 401、封禁 403、秘境入口 403（客户端原始 fetch 特殊消费，0.8.5 已处理）**不在**本案范围，保持原语义。
2. **动账全部服务端结算，沿用既有双原语**：扣款 `spendFromSave`（:9354，锁内二次校验）、发奖 `updatePlayerSave`。新端点零新增动账原语。
3. **「先占位 → 再动账 → 失败补偿」全或无**（0.8.6 铁律③）：审批入盟 = 先 `UPDATE` 申请行占位（changes=1 者）→ 守卫式 `INSERT sect_members` → 插入失败回滚申请行并 409。捐献回馈 = 先扣灵石成功 → 再写贡献（写失败仅损失回馈，不产生无对价扣款，可接受并记日志）。
4. **并发防重靠主键与部分唯一索引，不靠先查后写**：一人一 pending 申请 = `CREATE UNIQUE INDEX … ON sect_applications(user_id) WHERE status='pending'`（先例：`idx_mentorships_apprentice_active` :639）。
5. **日切统一 `bjDate`**（北京日切，:9348-9352 现成），与 `sect_ledger`/`sect_tasks` 同口径。
6. **频控沿用两桶**：读 `sectReadLimit` 60/min、写 `sectWriteLimit` 20/min（:9616-9617），新端点全部挂 `sectWriteLimit`（read 类挂 `sectReadLimit`）。
7. **玩法说明 = 客户端静态文案**（§8 全文），零新端点；两套宗门关系在文案中讲清。
8. **EV/产出红线**：仙盟无赔率类玩法；俸禄/任务奖励维持 V27 定值不动；捐献回馈产出的是「贡献」而非灵石（无灵石回流路径），并受日上限钳制（§6.4）。任何调参只动常量区（:9227-9257），不改逻辑。
9. **原生存档不写**：V27 入盟/退盟不碰 `player.sectId`（§1.4-3）；功法阁解锁仍按原生宗门口径，文案说明「参加原生仙门可开启功法阁」。

## 4. 玩法闭环设计（对应任务书七项）

### 4.1 盟列表与检索
- `GET /api/sect/list?page=&keyword=`：keyword 走师徒同款净化（trim 1..16 字 + `\ % _` 转义，:4739-4747 抄用）→ `WHERE name LIKE ? ESCAPE '\'`；排序维持等级→资金→id；分页 10/页不变。
- 响应行增加：`joinMode`（'auto'|'apply'）、`memberCount`、`leader`、`level`、`funds`。我的 pending 申请不在列表标（面板从 `mine` 取全局一份）。

### 4.2 申请加入（盟主审批 或 自动）
- `sects` 加列 `join_mode TEXT NOT NULL DEFAULT 'auto'`（存量盟自动=直进，向后兼容）。
- `POST /api/sect/join {sectId}` 语义分裂：
  - `auto`：现行为不变（满员 400 / 冷却 **409+cooldownLeftMs** / 已在盟 400）；
  - `apply`：改写申请行（守卫式 INSERT；同 user 已有任意 pending → 部分唯一索引挡下 → 409「已有待处理的申请」）；返回 `{message:'申请已提交，等待盟主审核'}`。
- 审批：`POST /api/sect/applications/decide {id, action:'approve'|reject'}`——
  1) 权限（盟主/长老，§3）；
  2) 占位：`UPDATE sect_applications SET status='approved', handled_at=?, handled_by=? WHERE id=? AND status='pending' AND created_at > ?`（第二条件=申请有效期 **72 小时**（数值已定档《数值表-T7T8》T7-6，常量 `SECT_APPLY_TTL_MS`；过期申请落 `expired` 由读取路径惰性置状态））；
  3) changes=1 者守卫式插入成员（复用 join 的满员/冷却/唯一索引全套核查）；
  4) 插入失败 → 回滚 `status='pending'`（保留 handled 置空）+ 409 带诊断文案（满员/冷却/已入盟，逐项诊断口径抄 mentor 拜师 :6518-6523、邮件先例 :6527-6532）；
  5) 成功 → `insertMail` 通知申请人（先例 :6527-6532）；reject 同样邮件告知。
- 撤销：`POST /api/sect/applications/cancel`——本人 `UPDATE … SET status='cancelled' WHERE user_id=? AND status='pending'`。
- 建宗即盟主，`join_mode` 默认 auto；创建端点 :9696 不动。

### 4.3 职位权限
端点全部存量（:9809-9894），仅状态码修正（§6.1）+ 面板 UI（§5）。角色字段沿用 `CHECK (role IN ('leader','officer','member'))`（:9290）。

### 4.4 盟任务与捐献
- 集体任务 4 项（围猎/历练/共修/捐献）与个人领取**原样保留**；捐献端点保留，仅追加 P1 回馈（§6.4）。
- 「先占位→扣款→补偿」现有实现已合规（:9914-9925），不动。

### 4.5 盟福利
俸禄（等级×500）+ 宗门凝气丹（2 级解锁）原样保留；数值调参只动 :9235-9237。

### 4.6 盟信息展示
- 面板 IA 见 §5；`/api/sect/mine` 扩展（N1）：`joinMode` / `myApplication` / `applications`（仅盟主长老可见）/ `cooldownUntil`（我方退盟冷却截止，前端渲染剩余时间）。
- 详情页（`GET /api/sect/:id` :10036）保留，面板「查看」跳详情（成员表 + 今日任务进度只读）。

### 4.7 退出 / 踢人冷却

## 8. 玩法说明（玩家可见文案，面板「玩法说明」折叠块全文）

> **仙盟是道友们结伴修行的帮派**：入盟可领每日俸禄、做盟任务拿灵石，盟升级后还能领宗门凝气丹。
>
> - **加入**：在列表直接加入「自动加入」的仙盟；标着「需审批」的仙盟要盟主或长老通过申请才能入盟，申请 72 小时内有效（可撤销）。

> - **退出与冷却**：退盟、被踢或盟解散后，24 小时内不能加入新仙盟。
> - **捐献**：每天最多捐 50,000 灵石帮仙盟升级；每次捐献还会额外获得捐献额 2% 的「宗门贡献」（每日至多 1,000 点，可在原生仙门的功法阁领悟传承功法）。
