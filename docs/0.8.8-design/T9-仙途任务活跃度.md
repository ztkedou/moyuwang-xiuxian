## 0. 一页结论

| 项 | 内容 |
|---|---|
| **现状一句话** | 「仙途任务」= 服务端 Y2 模块：**4 个任务、每个 25 分、满分 100；4 档宝箱只发灵石（合计 55,000/日，固定值不随境界缩放）** |
| **真正的病根** | 不是"奖励少"，是**奖励错配**：同一份 55,000 灵石，在炼气期 = **2.33 小时**挂机收益，在长生境 = **0.24 小时** —— **跨度 9.8 倍**。低境界过强、高境界形同虚设 |

## 1. 现状真相（0.8.7 `srv/index_v28.ts` 实测）

### 1.1 「仙途任务」到底是什么

**入口**：顶栏「仙途任务」按钮（`@774173`）/ 仙务面板 tab `quest`（`YLXW_TABS` `@832728`：`{ key:"quest", label:"仙途任务", group:0 }`）

**渲染组件**：`YlxwTQuest`（`@839754`）—— 读服务端 `/quest/summary`，渲染：

```
仙途任务 · 活跃度 {activity}
[去信箱]

活跃宝箱 25 · 奖励灵石 {reward}   [领取 / 已领取 / 活跃度未达]
活跃宝箱 50 · ...
活跃宝箱 75 · ...
活跃宝箱 100 · ...

{任务名}   {已达成 ? "已完成" : "progress/target"}
...
```

原文（`@839754` 逐字）：
```js
children: "仙途任务" + (l ? " · 活跃度 " + YlxwNum(l.activity) : "")
… children: "活跃宝箱 " + b.tier), " · 奖励灵石 ", …YlxwNum(b.reward) …
    b.claimed ? "已领取" : b.unlocked ? <按钮 领取> : "活跃度未达"
```

⇒ **「仙途任务」= 活跃度 + 活跃宝箱 + 任务进度列表**，是一个**服务端驱动的日活跃度系统**。

### 1.3 现状的 5 个问题

| # | 问题 | 依据 |
|---|---|---|
| **Q1** | **项目太少**：只有 4 条，且**分值全部 25**，无区分度、无梯度 | `QUEST_DEFS` `:3813` |
| **Q2** | **奖励错配（真正的病灶）**：只有灵石，且**固定值不随境界缩放** ⇒ 同一份奖励，炼气 2.33× 挂机时薪、长生 0.24× —— **跨度 9.8 倍**（详表见 §1.4） | `CHEST_REWARDS` `:3820` |
| **Q3** | **无周常/里程碑/周上限**：只有"日"这一个周期，玩家长线无目标 | 全表无 week 相关活跃度逻辑 |
| **Q4** | **覆盖玩法极窄**：只覆盖 打坐/战斗/历练/消费 4 类；炼丹、灵田、灵宠、秘境、仙盟、师徒、演武场、悬赏、行乐、抽奖、洞府、聊天…… **一个都没有** | `computeQuestDeltas` `:3840` 只有 4 个键 |
| **Q5** | **技术天花板**：`tickDailyQuests` 只能吃「存档差值」，凡是**不写进 `save_data` 的行为**都无法计入 —— 这才是"项目加不上去"的根本原因（不是策划懒） | `extractCounters` `:3827` |

### 1.4 Q2 的量化证明：现状奖励「错配」有多严重

`rainHourlyStones = floor(17676 × YLRF(realm))`（`数值表-T11` §4.3 同源；`YLRF`：炼气 4/3、筑基 3、金丹 5、元婴 7、化神 9、合道 11、长生 13）

| 境界 | 挂机时薪基准 | 现状日活跃度全清 55,000 | **= 几小时挂机收益** |
|---|---:|---:|---:|
| 炼气期 | 23,568 | 55,000 | **2.33×** |
| 筑基期 | 53,028 | 55,000 | 1.04× |
| 金丹期 | 88,380 | 55,000 | 0.62× |
| 元婴期 | 123,732 | 55,000 | 0.44× |
| 化神期 | 159,084 | 55,000 | 0.35× |
| 合道期 | 194,436 | 55,000 | 0.28× |
| 长生境 | 229,788 | 55,000 | **0.24×** |

⇒ 炼气 2.334 ÷ 长生 0.239 = **9.77 倍**。**同一个系统，对新手是"重要收入"，对老玩家是"可以无视"** —— 这是"内容太简单"之外、用户没直接说出来但更致命的缺陷。

### 1.5 顺带澄清：与「日常任务」是两个系统（易混淆）

| 系统 | 位置 | 内容 | 数据源 |
|---|---|---|---|
| **仙途任务**（本文对象） | 仙务面板 tab `quest` / 顶栏按钮 | 活跃度 + 活跃宝箱 + 4 条计分任务 | **服务端** `/quest/summary` |
| **日常任务**（原生，**不在本文范围**） | 顶栏「日常」按钮（蓝角标 `完成数/总数`） | 客户端本地随机 10~20 条任务（`$3` 池 28 条，`hg()` 结算），奖励灵石+修为+抽奖券 | **客户端** `player.dailyQuests` |

- 客户端生成逻辑：`const v=Math.floor(Math.random()*11)+10` ⇒ **每日 10~20 条**（`@1566741`）
- 面板组件 `TM` `@1441211`，标题字面 `"日常任务"` `@1442079`（含 `"第 {gameDays} 天"`）
- 任务池 `$3` 28 条（8 类 × 品阶），奖励公式 `hg()`；0.8.6 已把灵石 ×5

> ⚠️ **两个系统都叫"任务"、都按日重置、都发灵石**，玩家极易混淆。本设计**保留两者**（职责不同），但建议把原生那个**改名**（见 §5.4）。

## 2. 重构总纲

### 2.1 设计目标（对标主流网游活跃度体系）

1. **项目丰富**：覆盖游戏内**全部主要玩法**，玩家"随便怎么玩"都能攒分。
2. **分值有梯度**：核心行为低分高频、长线行为高分低频，避免"全是 25 分"。
3. **奖励有层次**：日档位（即时反馈）+ 周里程碑（长线目标）+ 稀有掉落（惊喜感）。
4. **奖励随境界缩放**：**修正 Q2 的 9.8 倍错配** —— 全境界恒定倍数。
5. **不做通胀 faucet**：全清产出必须**低于**同时间的主动玩法产出，且**有日/周硬上限**。

### 2.2 三条硬约束（本设计的自我约束）

| 约束 | 内容 | 理由 |
|---|---|---|
| **C1 日上限** | 单日活跃度 = 名义总分 330，**超出不累计** | 防"刷分"，与现有 `MIN(target, progress+delta)` 封顶口径一致（`tickDailyQuests` `:5045`） |
| **C2 周上限** | 周活跃度 ≤ 7 × 330 = **2,310** | 防跨日刷 |
| **C3 产出锚定** | 全清（260 档）日灵石 = **2.32 × 挂机时薪基准**（跨境界恒定）；日+周全清 = **3.33 × 周挂机时薪基准** | 与 `数值表-T11` §4.3 的 `rainHourlyStones` 口径对齐；且**远低于主动玩法时薪**（T11 表4：主动历练时薪 = 2.3~23× 基准 **每小时**） |

| 合道期 | 55,000 | 451,000 | +720.0% | 2.320× |
| 长生境 | 55,000 | 533,000 | **+869.1%** | 2.320× |

> **设计取舍（重要）**：本方案选择「**低境界一分不砍，高境界按境界补齐**」。
> 理由：① 砍低境界会让玩家觉得"重构反而变少"，负反馈；② 现状高境界活跃度（0.24× 时薪基准）本就是**形同虚设的缺陷**，修到 2.32× 是"补齐"不是"超发"；③ 2.32× 仍**远低于**主动玩法（T11 表4：炼气 L1 主动历练时薪 = 2.3× 基准**每小时**，全清一天只等于 2.32 小时挂机收益）。
> 若用户认为高境界 +869% 过大，备选是把比例压到 1.5×（则炼气 35,352 = **−36%**）—— 见 §11 拍板项 B。

- **修为**：见 §4.3
- **抽奖券**：19 张/日。对照自然产出（历练 lottery 事件占池 1/36、均值 5.5 券/次、600 次历练/h ⇒ **≈92 券/小时**），19 券/日**几乎可忽略**，不构成新 faucet ✅
- **灵石合计**：逐档 `floor` 后炼气 = **54,664**（表内 `41,000×4/3 = 54,667` 为公式直算值），差 3 灵石，无意义

### 4.3 修为奖励：为什么用「打坐等效次数」而不是「maxExp 百分比」

```
修为 = 打坐等效次数 × 打坐单次修为(realm, realmLevel)
打坐单次修为 = floor( f × 10 × (1 + realmLevel × 0.15) )     # 产物 @661082
f = [1, 2, 4, 8, 15, 30, 60][大境界序]
```

**理由（重要）**：

- 若用「当前层 `maxExp` 的百分比」，在高境界会**直接变成第二个跳境界通道**，与 item 7 传承设计（`T7-传承系统.md` §3.2）撞车 —— 传承已经把高境界的"百分比修为"占用了，活跃度再用同一量纲会**叠加放大**。
- 「打坐等效次数」的口径天然**回归性**（低境界占比高、高境界占比低），正好符合活跃度的定位：**帮新手追赶，不给高境界破坏长线**。

各境界的等效表：

| 大境界·层 | 打坐单次修为 | 全清 1,860 次修为 | 占该层 `maxExp` |
|---|---:|---:|---:|

| 炼气期 L5 | 17 | 31,620 | 26.9% |
| 筑基期 L1 | 23 | 42,780 | 11.0% |

> 全清活跃度 ≈ **31 分钟打坐**（1,860 次 × 1 秒，节拍假设见 `T7-传承系统.md` §2.3 脚注 F）。
> 对新手：约 1/3 个小境界；对高境界：可忽略 —— **这是有意设计**。高境界玩家的活跃度价值主要体现在**灵石**（2.32× 时薪基准）与**抽奖券/道具**上。

## 7. 实现方案（给实现批，本文不改码）

### 7.1 核心技术选型：读时计算（推荐）vs 写时埋点

**现状**：`tickDailyQuests`（`index_v28.ts:5045`）在 `POST /api/save` 里按**存档差值**推进 —— **只有 2 个调用点**（`:2151` / `:2174`，均在 `POST /api/save` 内，入参 = `computeQuestDeltas(prevCounters, extractCounters(saveData))`，`:3840`），**只能覆盖写进 `save_data` 的行为**。这是 Q4/Q5（项目加不上去）的根因。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **X · 读时计算**（★推荐） | `/api/quest/summary`（`:5432`）内对 18 条来源各跑一条「当日 COUNT/取值」，实时合成活跃度 | ① 改动集中在 **1 个接口**；② **零写埋点**，不碰 13 个业务端点；③ **天然幂等**，无并发丢更新；④ 新增来源只需加一条查询；⑤ **与本项目既有范式一致** —— Y19 成就注释明写"达成从 `stats_daily`/`daily_quests`/`saves` **惰性推导（零新增埋点零新增统计表）**"（`:4162`、`:9636-9637`） | summary 查询数 2 → ~20（可加 60s 缓存） |
| Y · 写时埋点 | 每个业务端点在成功时 `INSERT/UPDATE daily_quests`（c3 的 T16 §3.5 原主张此路，**c3 已复核放弃** ✅） | 查询快 | 13+ 处改动、每处都要处理并发与幂等、易漏埋点、且与客户端权威存档架构不一致 |

**推荐 X**。理由：本项目是"客户端权威存档 + 服务端只读"架构，读时计算与之一致；且 B/C/D 组的 13 个来源**全部已有服务端表**（§3 数据源列，已逐表核实），只需查询。

> ⚠️ **但 X 有一个必须处理的回归**：`daily_quests` 还被 **Y19 成就的 2 处累计 COUNT** 依赖（`:9646` / `:9678`）。**故本设计是"读时计算 + 保留 legacy 4 键写时推进"的混合式**，详见 **§7.6**。

### 7.6 ★ Y19 成就兼容（c3-design 实测发现，**必须处理，否则静默回归**）

**问题**：Y19 成就 `quest_1 / quest_10 / quest_50 / quest_200`（「小试牛刀 / 勤修不辍 / 任务达人 / 仙途楷模」，定义 `:4194-4197`）的达成条件是**累计完成每日任务数**，数据源是：

```sql
SELECT COUNT(*) AS c FROM daily_quests WHERE user_id = ? AND done = 1 AND quest_key NOT LIKE 'chest_%'
```

**读点 2 处，且都是「无日期维度的累计口径」**：`GET /api/achievements` **`:9646`** + `POST /api/achievements/claim` **`:9678`**（claim 是服务端重算，不达成直接拒绝）。

⇒ **若本设计「纯读时计算、不再落 `daily_quests` 行」，这两处 COUNT 会塌成 0 ⇒ 新玩家永远拿不到这 4 项成就**（已领的不退回，但成就线静默断裂）。**这是必须处理项，不是可选项。**

**本设计的处理（混合式，但收窄到「只保留 legacy 4 键」）**：

| 措施 | 说明 |
|---|---|
| **保留 `tickDailyQuests` 原样不动** | 继续为 **4 个 legacy 键**（`meditate` / `kill` / `adventure` / `spend`）写 `daily_quests` done=1 行 —— **Y19 口径 4 行/日，与现状 byte 级一致** |
| **14 个新项目不落 `daily_quests` 行** | 只走读时计算。**刻意不写**，否则 Y19 的计数会从 4/日 涨到 18/日 ⇒ `quest_200` 从 50 天加速到 ~11 天（**静默 buff Y19 4.5 倍**） |
| **计分用 `max(行值, 读时值)`** | legacy 4 键两套口径并存时取大，保证 `tick` 漏算不会漏分 |
| **`activityFromQuests` 的 2 个读取点全部改为「读时计算」** | 经实测（`grep -n activityFromQuests`）**全项目恰好 2 处调用**：**`:5457`**（`/api/quest/summary`，行读在 `:5435`）与 **`:5496`**（`/api/quest/chest`，行读在 `:5494`，判定在 `:5497`）。**两处都要改**：若只改 summary，chest 侧仍直读行 ⇒ 新 14 项不落行 ⇒ 活跃度被 legacy 4 键**封顶 100** ⇒ 第 5/6 档（200/260）**永不可解锁**、30/60/100 档也算少。**`chest_*` 占位行不动**（`:5507` 的 DELETE 回滚也不动）。<br>⚠️ **教训**：本设计初稿曾误写"这两处保留为兜底、无需改动"，导致 c3 把自己**正确的**实测判断改弱了。**同一语义有多份读取点，必须先 `grep` 数份数再下结论**（本项目铁律⑤「改过滤器先数份数」同条）。 |

> **拍板项 I 因此修正**：从"保留 `tickDailyQuests` 仅服务 2 键"改为"**原样保留 4 个 legacy 键**"。这是**唯一能让 Y19 零回归**的方案。
> **若将来要让 Y19 也计入新项目**，那是**独立的产品决策**（会加速 Y19 4.5 倍），不在 T9 范围 —— 需与 Y19 相关方单独拍板。
