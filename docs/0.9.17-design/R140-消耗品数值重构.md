# R-140 · 可使用物品（丹药 / 草药）数值重构 · 策划案

> 版本：0.9.17 设计稿 ｜ 作者：消耗品数值重构组主策划（design-r140）
> 基线：**0.9.16 线上版** `build/assets/index-v2916-20261003.js`（2,285,822 B，md5 `a59ac4496ab0e8ab81fdb147b45488ec`）
> 上游输入：`docs/0.9.17-design/侦察-物品与装备引擎全景.md`
> 需求原文（用户逐字）：
> 「所有可使用的如药草，丹药这些数值需要全部重构，因为这些东西不限量使用，如果数值过高会导致低等级轻易就能获得大量数值加强。一是可使用物品方面：低稀有度不加稀有属性，高稀有度数值减少并且售价提高，获取几率变小。那种升段位只能使用一次的奇物类道具不改。」
> **本轮只出设计，不改任何代码文件。** 所有函数偏移均已在本基线 bundle 上逐字复核。

---

## 0. 一句话结论

消耗品体系坏在**三个结构性缺陷叠加**：① `permanentEffect` 可无限叠加且 `$r` 递减永不归零；② `fg` 品质地板在**低境界**把高稀有度物品的地板值直接顶满；③ `Ic`/`DN` 在**低境界**就给 2× / 1.5× 的放大。三者相乘，使一个炼气期玩家吃 100 颗九转金丹可以拿到 **≈3.8 万攻击**（基准攻击仅 10）。
R-140 的解法是**「降源头 + 加硬顶」**：把品质地板与放大系数压到合理区间、重写爆表丹药、并给 `permanentEffect` 加**逐属性累计硬顶**（吃满即归零）。改完后同一场景下炼气期玩家的丹药攻击上限被钉死在 **+60**。

## 1. 问题陈述（逐条有据）

### 1.1 唯一非战斗服用结算口 `Ig`，只消费 4 类字段

`Ig(t, r, a)`（`@791084` 起）是**所有非战斗服用**（背包点击服用）的唯一结算函数。它只读：

| 字段 | 行为 | 备注 |
|---|---|---|
| `effect.hp` | `u.hp = min(maxHp, u.hp + effect.hp)` | **临时回血，不加上限** |
| `effect.exp` | `u.exp += effect.exp` | 永久加修为 |
| `effect.lifespan` | `u.lifespan = min(maxLifespan, lifespan + N)` | 临时补寿 |
| `permanentEffect.*` | 经 `$r` 折算后加到 `attack/defense/spirit/physique/speed/maxHp` | 永久属性；`maxLifespan` 直加；`spiritualRoots` 直加（单根 ≤100） |

**其余所有 effect 键在非战斗服用时全部无效**（已在 bundle 内逐键确认消费点 = 0）：
`spirit / physique / attack / defense / speed / soul / breakthrough / expRate / heal / regen / calm / removeDebuff / duration / critChance`。

> ★ 这意味着物品表里一大半字段是**死键**：写了不生效，玩家却以为是数值。这是「死键泛滥」问题（详见 §6）。

### 1.2 `permanentEffect` 无限叠加、永不归零 —— 用户抱怨的根因

```js
// @790672
const ZS=(t,r)=>{
  const a = Cs[t.realm] || Cs[ae.QiRefining],
        c = 1 + (Math.max(1, t.realmLevel||1) - 1) * 0.14,
        d = r==="maxHp" ? a.baseMaxHp : r==="attack" ? a.baseAttack :
            r==="defense" ? a.baseDefense : r==="spirit" ? a.baseSpirit :
            r==="physique" ? a.basePhysique : a.baseSpeed;
  return Math.max(r==="maxHp" ? 300 : 60, Math.floor(d * 1.35 * c));   // ← 软基准
};
// @790968
const $r=(t,r,a)=>{
  if(!Number.isFinite(a) || a<=0) return 0;
  const l = Number(t[r]) || 0, c = ZS(t,r);
  if(l <= c) return Math.floor(a);                       // 当前值 ≤ 基准 → 全额
  const d = Math.max(.25, Math.min(1, c / l));           // ← 下限 0.25，永不归零
  return Math.max(1, Math.floor(a * d));                 // ← 最少 +1，永不归零
};
```

- **无每日次数上限、无累计上限**：`Ig` 对每次服用都无条件执行 `$r` 并累加。
- **下限 25% + 最少 1 点**：即使当前属性是基准的 100 倍，每颗丹仍给 `floor(值×0.25)`；至少 +1。
- 结论：**数量可以无限兑换属性**，这就是「不限量使用」的机制漏洞。

### 1.3 `fg` 品质地板 —— 高稀有度在低境界直接「爆表」

```js
// @310384
fg = {
  普通: { hp: 80,   exp: 40,   spirit: 3,   physique: 3,   maxHp: 8   },
  稀有: { hp: 280,  exp: 180,  spirit: 12,  physique: 12,  maxHp: 35  },
  传说: { hp: 900,  exp: 700,  spirit: 55,  physique: 55,  maxHp: 120 },
  仙品: { hp: 2600, exp: 2200, spirit: 180, physique: 180, maxHp: 380 },   // ★ 元凶
};
Rr = 250;   // 仙品属性地板（yg 用）
mw = 5000;  // 仙品修为地板（yg 用）
```

在 `ry`（`@317832`）的消耗品分支里，地板是 `max(原值×b, fg[rarity].键)`：

```js
const f = fe.indexOf(a), v = f>=0?f:0, m = ny[v]||1,
      j = 1+(l-1)*.08, b = m*j,                    // effect 主系数
      S = Math.sqrt(m)*(1+(l-1)*.04), x = Math.min(1.5,S),  // permanentEffect 系数（封顶 1.5）
      M = fg[d] || fg.普通;
// effect：hp/spirit/physique/exp 走 max(floor(原值*b), M.键)；attack/defense/speed 无地板
// permanentEffect：spirit/physique/maxHp 走 max(floor(原值*S), M.键)；attack/defense/speed/maxLifespan 无地板
```

**后果**：在**炼气期**（`b` 很小），一件 `仙品` 物品的地板被顶到 `spirit≥180 / maxHp≥380 / exp≥2200 / hp≥2600`。例如 `仙灵丹`（传说，`perm.spirit:30`）经地板后变成 **55**；`九转金丹`（仙品）`perm.spirit:100` 经 `yg` 抬到 **250**。**低境界反而拿到最高地板** —— 这正是用户说的「低等级轻易就能获得大量数值加强」。

### 1.4 `Ic` / `DN` 在低境界就给 2× / 1.5× 放大

掉落/奖励路径（`Ym` → `Ic`，`@582596`）：
```js
// Ym 内：c=[1,1.237,1.53,1.892,2.341,2.895,3.582][realmIdx]; d=1+(realmLevel-1)*.3; u=c*d;
// Ic(effect, permanentEffect, rarity, u):  effect 每键 × (u*2)   permanentEffect 每键 × (u*1.5)
//   再 yg(值, rarity)：仙品时 exp≥5000、hp/attack/defense/spirit/physique/speed≥250
```
- 炼气期 L1（`u=1`）：effect **×2**、permanentEffect **×1.5**。
- 长生境 L9（`u≈12.18`）：effect **×24.4**、permanentEffect **×18.3**。

炼丹路径（`@819457` → `DN`，`@321629`）：
```js
DN(effect, permanentEffect, purity): effect × (1.5+(purity-60)*0.025)，permanentEffect × (1+(purity-60)*0.0125)
```
- 纯度 60 → effect ×1.5 / perm ×1.0；纯度 100 → effect ×2.5 / perm ×1.5。
- ⇒ **炼丹路径**与**掉落路径**在炼气期的永久属性放大几乎一致（都 ≈1.5×），两条路都需一起改。

### 1.5 实测爆表算例（现行，未改）

**场景：炼气期 L1 玩家（attack 10 / defense 5 / spirit 5 / physique 10 / speed 10 / maxHp 100），无限吃 `九转金丹`（仙品）。**

九转金丹 `permanentEffect:{attack:1000, defense:1000, spirit:100, physique:100, speed:100}`：
- 经 `Ic`（炼气 L1，`u=1`，perm ×1.5）→ attack 1500 / defense 1500 / spirit 150 / physique 150 / speed 150
- 经 `yg`（仙品地板 `Rr=250`）→ attack 1500 / defense 1500 / **spirit 250 / physique 250 / speed 250**
- 第 1 颗：当前 attack 10 ≤ ZS 60 → **全额 +1500** ⇒ attack 1510
- 第 2 颗：当前 1510 > 60 → `d = max(.25, 60/1510) = 0.25` ⇒ +375 ⇒ 1885
- 第 n 颗：每颗恒 **+375**（下限 0.25 封住）⇒ 吃 100 颗后 **attack ≈ 10 + 1500 + 99×375 = 38,635**

**炼气期基准攻击只有 10。** 这就是用户投诉的量化原形。

### 1.7 授予管道 `vs()` —— 消耗品最终数值的真正落点（R-141 共享，已复核）

所有物品进入背包都要经 `vs(t, r, a=1, l)`（`@632245`）。对 R-140 有 4 条关键事实：

```js
function vs(t, r, a=1, l) {
  // …解析 type / rarity…
  const x = LN(d, r.effect, r.permanentEffect);   // ① effect/permanentEffect 归一化
  let T = x.effect, $ = x.permanentEffect;
  if (l) {                                        // ② l = 玩家上下文（有则触发缩放）
    // 装备：$ 的 attack/defense/spirit/physique/speed 并入 T，maxHp→hp，$ 置 undefined
    const h = ry(T, $, l.realm, l.realmLevel, j, v, r.realm);   // ★ 消耗品/装备的最终缩放
    T = h.effect; $ = h.permanentEffect;
  }
  // ③ 装备分支：显式白名单重建物品对象（不 spread r）
  // ④ 消耗品分支：按 name 合并到已有堆（effect/permanentEffect 被新值覆写）
}
```

1. **消耗品最终数值 = `ry(effect, permanentEffect, 玩家realm, 玩家realmLevel, type, rarity)`**。因此 §3.1 的 `fg`、§3.3 的 `ny` 修改**在授予时真实生效**，注入点正确；`Ic` 则在事件结算 `Ym()` 内生效 —— **两条路都要改**（§3.2 已覆盖）。
2. **`ry` 第 7 参 `noScale`（`r.realm`）只对装备短路，对消耗品无效** ⇒ 消耗品**永远**吃 `ny`/`fg` 缩放（这进一步说明 `ny` 不能乱动）。
3. **装备分支用白名单重建**：`{id,name,type,description,quantity,rarity,level,effect,permanentEffect,isEquippable,equipmentSlot,realm,recipeData,reviveChances,advancedItemType,advancedItemId}` —— **不在白名单的额外字段会被静默丢弃**。⇒ 实施者**不能**靠「给物品对象加新字段」来实现 R-140；本方案的 `permGain` 挂在**玩家对象**上，不受影响。
4. **消耗品按 `name` 合并堆**：`c[M] = {...c[M], effect:T, permanentEffect:$, quantity:+a}` ⇒ 同名消耗品**再次获得时，整堆的 effect/permanentEffect 被新值覆写**。这意味着「存量旧值物品」在**下一次获得同名物品**时会被顺带刷新为新值 —— 部分缓解 §8.2 的存量快照问题（但不能保证每个存量物品都被刷新）。

## 2. 设计目标（对齐用户原话）

| # | 用户原话 | 设计目标 | 落地手段 |
|---|---|---|---|
| G1 | 「低稀有度不加稀有属性」 | 普通/稀有物品**不得**通过品质地板凭空获得 `spirit/physique/speed` | `fg.普通/稀有` 的 `spirit/physique` 置 **0**；掉落生成时低品质不 roll 稀有属性 |

## 3. ★ 核心数值表

### 3.1 新 `fg` 品质地板表

```js
// 新 fg（改 @310384 一处）
fg = {
  普通: { hp: 20,  exp: 12,  spirit: 0,  physique: 0,  maxHp: 3   },
  稀有: { hp: 70,  exp: 45,  spirit: 0,  physique: 0,  maxHp: 10  },
  传说: { hp: 220, exp: 170, spirit: 12, physique: 12, maxHp: 30  },
  仙品: { hp: 650, exp: 550, spirit: 40, physique: 40, maxHp: 95  },
};
```

| 品质 | hp | exp | spirit | physique | maxHp |
|---|---|---|---|---|---|
| 普通（新） | 20 | 12 | **0** | **0** | 3 |
| 普通（旧） | 80 | 40 | 3 | 3 | 8 |
| 稀有（新） | 70 | 45 | **0** | **0** | 10 |
| 稀有（旧） | 280 | 180 | 12 | 12 | 35 |
| 传说（新） | 220 | 170 | 12 | 12 | 30 |
| 传说（旧） | 900 | 700 | 55 | 55 | 120 |
| 仙品（新） | 650 | 550 | 40 | 40 | 95 |
| 仙品（旧） | 2600 | 2200 | 180 | 180 | 380 |

**推导理由**：
1. **普通/稀有 `spirit/physique` 置 0**（实现 G1）。`ry` 里地板写法是 `M.spirit ? Math.max(h, M.spirit) : h`，`0` 为 falsy ⇒ 自动跳过地板，不会凭空加稀有属性。低稀有度物品若想有稀有属性，必须**显式**在数据里写，且不再被地板抬高。
2. **整体压到约旧值的 1/4**。地板的作用是「保底不寒碜」，不是「拉满」。旧地板在低境界就是实际数值（因为 `b` 小），压到 1/4 后低境界高稀有掉落不再爆表。
3. **传说/仙品的 `spirit/physique` 保留非零地板**（12 / 40），因为「高稀有度可以有稀有属性，但值要小」，同时与 §3.4 的硬顶（炼气期 cap ≈ 60）配合，单件不会顶穿硬顶太多。
4. `hp/exp/maxHp` 地板同步压到约 1/4，避免高稀有度物品在低境界「白送」巨额修为/血线。

### 3.2 新 `Ic` 系数

```js
// Ic（@572462）改两处：
effect:          × (u * 1.0)    // 原 × (u * 2)
permanentEffect: × (u * 0.8)    // 原 × (u * 1.5)
// 其中 u = realmTierCoeff = c * d，c=[1,1.237,1.53,1.892,2.341,2.895,3.582][realmIdx]，d=1+(realmLevel-1)*0.3
```

| 境界 / 层 | u | effect 旧→新 | perm 旧→新 |
|---|---|---|---|
| 炼气 L1 | 1.00 | ×2 → **×1.0** | ×1.5 → **×0.8** |
| 筑基 L1 | 1.24 | ×2.47 → **×1.24** | ×1.86 → **×0.99** |
| 金丹 L1 | 1.53 | ×3.06 → **×1.53** | ×2.30 → **×1.22** |
| 元婴 L1 | 1.89 | ×3.78 → **×1.89** | ×2.84 → **×1.51** |
| 化神 L1 | 2.34 | ×4.68 → **×2.34** | ×3.51 → **×1.87** |
| 合道 L1 | 2.90 | ×5.79 → **×2.90** | ×4.34 → **×2.32** |
| 长生 L9 | 12.18 | ×24.36 → **×12.18** | ×18.27 → **×9.74** |

**推导理由**：
1. `effect` 改 `u*1.0`：**炼气期不再有 2× 白送**；高层仍随 `u` 线性增长（成长感保留，只是斜率减半）。
2. `permanentEffect` 改 `u*0.8`：永久属性**比瞬时属性更值钱**（可叠加、永久），源头应更保守；炼气期 `×0.8` 让「1 颗顶 1.5 颗」的旧行为消失。
3. 不改 `u` 的构成（`c*d`）——它是全局等级曲线，动它影响面过大（会波及 `Ym` 的修为/灵石缩放）。

同时下调 `yg` 的仙品地板：
```js
Rr: 250 → 40     // 仙品属性地板（原 250）
mw: 5000 → 1200  // 仙品修为地板（原 5000）
```
理由：旧值 250 高于炼气/筑基/金丹的 `ZS`（=60），导致一颗仙品丹瞬间顶穿硬顶；降到 40 后单颗丹约需 2 颗才到顶，保留「仙品更强」的体感。

`DN`（炼丹纯度，`@321629`）建议同步下调：
```js
effect:          × (1.2 + (purity-60)*0.02)   // 原 1.5 + *0.025  ⇒ 纯度60: 1.2(原1.5)，纯度100: 2.0(原2.5)
permanentEffect: × (0.7 + (purity-60)*0.01)   // 原 1.0 + *0.0125 ⇒ 纯度60: 0.7(原1.0)，纯度100: 1.1(原1.5)
```

### 3.3 新 `ny` 境界系数

### 3.4 ★ `permanentEffect` 叠加约束方案（核心机制）

> 这是本轮**最重要的机制改动**，直接兑现 G5「不限量使用不再能无限换属性」。

#### 机制：逐属性「累计硬顶」+ `$r` 递减加强

**① 新增玩家字段 `permGain`**（默认 `{}`，向后兼容）
记录**由消耗品来源**累计获得的永久加成：
```js
permGain: { attack?, defense?, spirit?, physique?, speed?, maxHp? }   // 仅消耗品贡献
```

**② 硬顶公式**
```js
YLXW_R140_PERM_CAP_RATIO = 1.0;                       // 累计上限 = 1.0 × ZS
cap(player, key) = YLXW_R140_PERM_CAP_RATIO * ZS(player, key)
```
`ZS` 复用现有函数（`@790672`），即「该境界该属性的自然基准值」。语义：**丹药对某属性的累计贡献，不得超过该境界的自然基准**。低境界 `ZS` 被 `max(60,...)` 兜底，所以炼气/筑基/金丹的丹药累计上限都在 **+60 左右**；随境界自然放开。

**③ `Ig` 内改法（唯一改动点）**
```js
// 对 permanentEffect 的每个键：
const g   = $r(u, key, R[key]);                    // 现有递减
const room = Math.max(0, cap(u, key) - (u.permGain?.[key] || 0));
const g2  = Math.min(g, room);                     // ← 硬顶
if (g2 > 0) { u[key] += g2; u.permGain[key] = (u.permGain?.[key]||0) + g2; }
else        { log(`【${r.name}】的 ${key} 增益已达本境界上限，未生效。`); }
```
（`maxHp` 同步 `u.maxHp += g2; u.hp += g2`；`spiritualRoots` 不受此限，单根已 ≤100。）

**④ `$r` 递减加强（次要平滑）**
```js
d = Math.max(0.25, Math.min(1, c/l))  →  d = Math.max(0.10, Math.min(1, c/l))
```
把下限从 25% 降到 10%，让「接近硬顶时」单次增益更小，过渡更顺滑。**注意：仅靠改 `$r` 无法封顶**（`Math.max(1,...)` 保底 +1），所以硬顶是主机制、`$r` 是辅助。

**⑤ `maxLifespan` 独立硬顶**
```js
YLXW_R140_LIFE_CAP_RATIO = 0.2;
cap = 0.2 * Cs[realm].baseMaxLifespan   // 炼气+20 / 筑基+40 / 金丹+90 / 元婴+200 / 化神+400 / 合道+800 / 长生+1600
```

#### ★ 数值算例：炼气期玩家吃满某丹后最多能拿到多少属性

**基准（炼气期 L1）**：`Cs.炼气 = { baseMaxHp:100, baseAttack:10, baseDefense:5, baseSpirit:5, basePhysique:10, baseSpeed:10 }`
`ZS(炼气 L1) = { attack:60, defense:60, spirit:60, physique:60, speed:60, maxHp:300 }`
`cap = 1.0 × ZS = { attack:+60, defense:+60, spirit:+60, physique:+60, speed:+60, maxHp:+300 }`

**算例 A —— 无限吃「九转金丹」（仙品）**
- 重做后 `perm = {attack:120, defense:120, spirit:20, physique:20, speed:20}`
- 经新 `Ic`（炼气 L1，perm ×0.8）→ attack 96 / defense 96 / spirit 16 / physique 16 / speed 16
- 经新 `yg`（仙品地板 `Rr=40`）→ attack 96 / defense 96 / spirit 40 / physique 40 / speed 40
- 逐颗结算（初始 attack 10 / defense 5 / spirit 5 / physique 10 / speed 10）：

| 颗数 | attack | defense | spirit | physique | speed |
|---|---|---|---|---|---|
| 0（初始） | 10 | 5 | 5 | 10 | 10 |
| 1 | **70**（+60 顶满） | **65**（+60） | 45（+40） | 50（+40） | 50（+40） |
| 2 | 70（顶） | 65（顶） | **65**（+20 顶满） | **70**（+20 顶满） | **70**（+20 顶满） |
| 3…∞ | 70 | 65 | 65 | 70 | 70 |

**⇒ 炼气期玩家吃满九转金丹后的永久属性上限 = attack 70 / defense 65 / spirit 65 / physique 70 / speed 70，第 3 颗起全部归零。**
**对照现行**：第 100 颗后 attack ≈ **38,635**。**降幅 ≈ 552×**，且**有硬顶、不可再涨**。

**算例 B —— 无限吃「洗髓丹」（稀有，`perm.maxHp:30`）**
- 经新 `Ic`（perm ×0.8）→ 24；经 `fg.稀有.maxHp=10` 地板 → 24
- `cap(maxHp) = +300`；初始 maxHp 100
- 每颗 +24（当前 maxHp ≤ 300 前全额），第 13 颗到顶
- **⇒ 上限 maxHp 400（+300），第 13 颗起归零。**

**结论**：稀有丹需 ~13 颗到顶、仙品丹需 ~3 颗到顶 —— **品质差异保留，但都不再有「数量碾压」**。

**简化备选（若不愿加 `permGain` 存档字段）**：不做累计追踪，直接 `if (u[key] >= cap(player,key)) g = 0;`。代价：把装备/等级贡献也算进 `cap`，可能导致「装备好的低境界玩家吃丹无效」。**推荐主方案（带字段）**，语义更干净、且旧档加载时 `permGain` 默认为 `{}`，天然兼容。

## 4. 售价调整

### 4.1 现状

唯一价格出口 `YlxwShopPriceOf(it, player)`（`@1812168`）：
```js
var base = Rm(it.price, player), g = YlxwShopTierGap(it, player);
if (g > 0) base = Math.max(1, Math.ceil(base * Math.pow(YLXW_SHOP_TIER_DOWN, g)));
var mul = YlxwR135HasRareAttr(it) ? YLXW_R135_RARE_PRICE_MUL    // = 6
                                  : YLXW_R135_BASE_PRICE_MUL;   // = 1.5
return Math.max(1, Math.ceil(base * mul));
```
R-135 的二元乘数（×6 有稀有属性 / ×1.5 其余）**与品质无关**：一件 `普通` 带 `spirit` 的物品也吃 ×6，而 `仙品` 无稀有属性只吃 ×1.5。这与用户「高稀有度售价提高」的诉求**方向不一致**。

### 4.2 新方案：品质阶梯乘数（**替换** R-135 二元乘数）

```js
// 新增常量（@1811587 附近）
var YLXW_R140_CONSUM_PRICE_MUL = { 普通: 1.5, 稀有: 3, 传说: 6, 仙品: 12 };
var YLXW_R140_CONSUM_PRICE_KEYS = ["丹药", "草药"];   // 仅对消耗品生效

// YlxwShopPriceOf 内：
var isConsum = (it.type === "丹药" || it.type === "草药");
var mul;
if (isConsum) {
  mul = YLXW_R140_CONSUM_PRICE_MUL[it.rarity] || YLXW_R140_CONSUM_PRICE_MUL.普通;
} else {
  mul = YlxwR135HasRareAttr(it) ? YLXW_R135_RARE_PRICE_MUL : YLXW_R135_BASE_PRICE_MUL;  // 装备沿用 R-135
}
```

| 品质 | 旧乘数（R-135） | **新乘数（R-140）** | 说明 |
|---|---|---|---|
| 普通 | ×1.5（无稀有属性）/ ×6（有） | **×1.5** | 普通不再可能带稀有属性（G1），故无 ×6 分支 |
| 稀有 | ×1.5 / ×6 | **×3** | 中等 |
| 传说 | ×1.5 / ×6 | **×6** | 与旧「有稀有属性」持平 |
| 仙品 | ×1.5 / ×6 | **×12** | 高稀有度显著提高（G3） |

**与现有 `×6`/`×1.5` 的关系**：
- **对消耗品（丹药/草药）：替换。** 品质阶梯取代二元乘数。
- **对装备/其他类型：保持不变**（继续走 R-135 的 `YlxwR135HasRareAttr ? 6 : 1.5`），避免波及 R-141 与装备经济。
- 基础价 `it.price` 来自商店池 `Ut(name, price, sellPrice)` 或动态池（`$M.forEach` 生成的 `普通 50–150 / 稀有 200–500 / 传说 1000–3000 / 仙品 5000–15000`）。**不动基础价**，只改乘数。

### 4.3 自售价（卖出）侧

自售价走 R-107 的独立链路（`YLSellCredit` + `YLXW_SELL_CAP_RATIO = 0.3`），**本轮不动**。但由于 §3.5–3.7 把 `permanentEffect` 大幅下调，估值器 `xm()` 的 `ΣpermanentEffect×权重` 会自动下降 ⇒ **掉落物的自售价自然回落**，与「高稀有度数值减少」自洽。无需额外改 `xm`。

## 6. 死键处置

| effect 键 | 出现物品 | 建议 | 工作量 |
|---|---|---|---|
| `spirit` / `physique` / `attack` / `defense` / `speed`（写在 **effect** 里） | 仙灵丹/结金丹/凝魂丹/凤凰涅槃丹/龙血丹/凝神花 | **接线**：把值**迁移到 `permanentEffect`**（`Ig` 已支持），或删除 | **数据层**，改物品表，零引擎改动。中 |
| `heal` | 回春丹 | **接线**：键名改为 `hp` | 数据层，极小 |
| `duration` | 大力丹/定神丹/神行丹/聚气丹/金刚丹/强体丹/灵识丹 | **废弃删除**（临时 buff 系统从未实现） | 数据层，小 |
| `expRate` | 聚气丹 | **废弃删除**（或接线为临时修为加成 → 需新建 buff 系统，本轮不做） | 数据层，小 |
| `regen` | 万木灵芽 | **废弃删除** | 数据层，极小 |
| `calm` | 定神丹 / 幽冥草 | **废弃删除** | 数据层，极小 |
| `removeDebuff` | 清心丹 | **废弃删除** | 数据层，极小 |
| `soul` | 凝魂丹 | **废弃删除**（无神魂系统） | 数据层，极小 |
| `critChance` | 雷音花 | **废弃删除**（`xs()` 白名单不含 + `Ig` 不消费，双重死键） | 数据层，极小 |
| `breakthrough` | 奇物类 7 条 | **不动** | — |

**接线 vs 废弃的原则**：
- **接线的**：语义本就该是「永久提升」且 `Ig` 已支持的（`spirit/physique/attack/defense/speed`、`heal→hp`）——**迁移到 `permanentEffect`**，不新增引擎代码。
- **废弃的**：需要**引擎侧新机制**才能生效的（临时 buff、神魂、清 debuff、暴击率）——本轮**删除字段**，避免玩家误解；若未来要做「临时 buff 系统」，单独立项。
- **推荐**：优先「接线」（把 effect 的永久属性搬到 permanentEffect），因为它同时解决「数值不生效」和「玩家以为有效」两个问题，且零引擎风险。
