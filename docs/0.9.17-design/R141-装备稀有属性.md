# R-141 高品质装备稀有属性（吸血 / 暴击率 / 暴伤 / 闪避）策划案

> 版本：0.9.17 设计稿 ｜ 基线：**0.9.16 线上版**（`build/assets/index-v2916-20261003.js`，2,285,822 B，md5 `a59ac4496ab0e8ab81fdb147b45488ec`）
> 作者：装备稀有属性组 ｜ 类型：**纯设计，零代码补丁** ｜ 目标：可直接交付程序员写补丁
> 需求原文：「把品质高的装备属性增加一些稀有属性，比如吸血，暴击率，爆伤，闪避……稀有属性主要出现在高品质的装备中，且低段位加成非常少，随等阶慢慢增加。神识、身法这些装备可以不改。」

---

## 0. 一句话结论

**稀有属性（暴击率 / 暴伤 / 闪避 / 吸血）的「生成 → 聚合 → 封顶 → 战斗消费」链路早已全套实装，只是掉落装备从不天生带词条。**
R-141 的本质 = **在高品质装备进入背包时，按「境界因子 × 品质」原生挂一组稀有词条**，消费层几乎零改动。
本文的核心新增物只有 **1 张境界因子表 + 1 张品质条数表 + 1 个折扣常数 + 1 个生成函数**，以及**在 `vs()` 授予管道注入 + 在 2 处聚合函数读取新字段**。

---

## 1. 问题陈述

### 1.1 现状：链路在，词条不在

| 环节 | 位置 | 状态 |
|---|---|---|
| 词条生成器 | `YlxwRF_Roll(rarity, count, excluded)` @1360982 | ✅ 已实装（洗炼用） |
| 词条存储 | `item.reforgeAffixes: [{type,name,value}]` | ✅ 已实装 |
| 战斗聚合 | `YlxwBattleBonus(p)` @1316967 装备层遍历 `reforgeAffixes` | ✅ 已实装 |
| 属性聚合 | `YlxwStatExtras(p,r)` @7505 处理 `attackPercent/defensePercent/hpPercent` | ✅ 已实装 |
| 统一封顶 | `YlxwBattleCap(o)` + `YlxwBattleCapCfg` @10194 | ✅ 已实装 |
| 战斗消费 | 快速战斗 `X0` @~764512 / 回合制 `km`（普攻）/`zy`（技能） | ✅ 已实装 |
| **掉落装备天生词条** | `cy()` / `_y()` / `vs()` | ❌ **缺失** |

⇒ 玩家今天只能花「太虚洗炼石」手动 roll 词条；**掉落的高品质装备天生一个稀有词条都没有**。

### 1.2 成因（为什么不能走 `effect` 字段）

装备 `effect` 的唯一提取器 `xs(item, isNatal)` @319785 返回**硬编码白名单**：

```js
{ attack, defense, hp, exp, spirit, physique, speed }   // 无 critChance / dodge / lifeLeech
```

往 `effect` 里写 `critChance`/`dodge`/`lifeLeech` 会被**静默丢弃**（全物品表唯一的 `雷音花 critChance:0.1` 就是这么废掉的）。
**唯一正确通路 = `reforgeAffixes`（或同构的新字段），它被 `YlxwBattleBonus` 与 `YlxwStatExtras` 直接消费。**

### 1.3 ★ 对侦察报告的一处重要修正（注入点）

侦察报告 §3.6 认为 `cy()` @464464 是「掉落/奖励装备进入世界的唯一构造点」。**经核对基线 bundle，此结论不完整：**

| 路径 | 是否经 `cy()` | 证据 |
|---|---|---|
| 抽奖成品 `vo`/`w3` | ✅ 经 `cy` | `function w3(t){const r=cy({...t,count:1});...}` |
| 秘境兜底掉落 | ✅ 经 `cy` | `cy({type:_t,realm:t.realm,realmLevel:t.realmLevel,count:1})` |
| **历练 / 秘境主掉落** | ❌ **不经 `cy`** | `_y=(t,r,a,l)=>{...}` 直接从 `gs.weapons/gs.armors/...` 取基座并 `c.push({...,effect:q.effect,...})` |
| 商店库存构造 | ✅ 经 `cy` | `$M.forEach(...cy({type,rarity,count:5}))`（无 realm） |
| **具名授予（任务/邮件/商店购买/活动）** | 经 **`vs()`** | `function vs(t,r,a=1,l){...}` 是唯一把物品对象**最终定型**的函数 |

**关键事实：`vs(t, r, a=1, l)` 是所有物品进入背包的最终重建点。** 它在 `if(b)`（`b = isEquippable`）分支里**逐字段显式重建**物品对象（`{id,name,type,description,quantity,rarity,level,effect,permanentEffect,isEquippable,equipmentSlot,realm,recipeData,reviveChances,advancedItemType,advancedItemId}`），**任何不在这个列表里的额外字段都会被丢弃**。

因此：
- 在 `cy()` 里挂的词条，物品被 `vs()` 领取时会**被丢掉**；
- 在 `_y()` 里挂的词条同样**会被丢掉**；
- **唯一有效且通用的注入点 = `vs()` 的 `if(b)` 分支**（紧跟 `ry(...)` 缩放之后）。

> 这一修正把「覆盖全部掉落/奖励路径」从 3 处注入收敛为 1 处，风险更低。

## 2. 核心设计：境界因子（低段位极少，随等阶递增）

### 2.1 现有缺口

`YlxwRF_Roll(rarity, ...)` **只吃 rarity，不吃境界**（`cfg = YlxwRF_Cfg(rarity)`）。这正是「低段位加成非常少、随等阶慢慢增加」需要补的维度。

### 2.2 境界因子表 `YlxwInnateRealmFactor`（7 档，对齐 `fe` 数组）

```js
var YlxwInnateRealmFactor = {
  "炼气期": 0.05,  "筑基期": 0.10,  "金丹期": 0.20,  "元婴期": 0.35,
  "化神期": 0.55,  "合道期": 0.80,  "长生境": 1.00
};
```

**推导**：
- 客户端境界枚举 `ae`/`fe` 共 **7 档**：`炼气期 筑基期 金丹期 元婴期 化神期 合道期 长生境`。
- 该曲线是**凸函数**（增长越来越快），刻意让前 3 档近乎可忽略：炼气仅 5%、筑基 10%、金丹 20%。
- 与现有 `ny = [1, 1.25, 1.75, 2.5, 3.5, 5, 7]` 的关系：`ny` 描述的是**基础属性数值**随境界的放大（长生是炼气的 7 倍），**不适合直接复用**——若用 `ny/7`，炼气就有 14.3%，达不到「非常少」的要求。故**独立新增本表**，不动 `ny`。
- 长生 = 1.00，保证**顶阶装备的天生词条强度 = 一次洗炼 roll 的基准强度**（不额外超发）。

### 2.3 与 `YlxwRF_RARITY` 的组合方式：**乘法**

```
最终数值 = randInt区间(YlxwRF_RARITY[rarity].minV ~ maxV)
         × YlxwRF_SPECIAL[type]        // 稀有键折扣（critRate .35 / critDamage .5 / dodge .3 / lifeLeech .25）
         × YlxwInnateRealmFactor[realm] // ★ 新增：境界因子
         × YlxwInnateK                  // ★ 新增：天生折扣 = 0.35
```

**为什么乘 `YlxwInnateK = 0.35`？**
洗炼是**花资源、可反复重投**的行为，天生词条是**免费、不可选择**的。若不折扣，顶阶天生词条会直接替代洗炼，洗炼系统失去意义。取 0.35（≈1/3）使：

- 天生词条 ≈ 洗炼词条的 1/3 强度 ⇒ **天生是「开胃菜」，洗炼仍是「主菜」**；
- 顶阶（长生·仙品）单条词条量级落在 1%–4%，**可感知但不破坏平衡**；
- 低段位（炼气·仙品）单条 < 0.2%，**名副其实的「非常少」**。

> 备选方案（若团队觉得常数晦涩）：把 `minV/maxV × 0.35` 固化成一张新表 `YlxwRF_RARITY_INNATE`，代码只做「查表 × 境界因子」。本文主推「常数乘法」，改动面最小。

## 3. 品质门槛：哪些品质生成、各几条

### 3.1 规则 `YlxwInnateCount`

```js
var YlxwInnateCount = { "普通": 0, "稀有": 1, "传说": 2, "仙品": 3 };
```

| 品质 | 天生词条条数 | 说明 |
|---|---|---|
| 普通 | **0** | 「稀有属性主要出现在高品质装备中」⇒ 普通装备不生成 |
| 稀有 | 1 | 低阶小惊喜 |
| 传说 | 2 | 中高阶明显收益 |
| 仙品 | 3 | 顶阶标志性收益 |

### 3.2 与现有 `YlxwRF_RARITY` 的关系：**条数新表、数值复用**

- **条数**：`YlxwRF_RARITY` 的 `minA/maxA`（普通1 / 稀有1-2 / 传说2-3 / 仙品3）是**洗炼**用的**随机区间**；天生词条用**固定条数** `YlxwInnateCount`（0/1/2/3），语义更清晰、便于封顶推导与断言。
- **数值**：直接复用 `YlxwRF_RARITY[rarity].minV/maxV` 与 `YlxwRF_SPECIAL`，不新增数值表（除 `YlxwInnateK`）。
- **类型池**：复用 `YlxwRF_TYPES`（7 类：`attackPercent/defensePercent/hpPercent/critRate/critDamage/dodgeRate/lifeLeech`），同一件装备内**去重抽取**（与 `YlxwRF_Roll` 一致）。

**为什么类型池用 7 类而不是只取 4 类稀有键？**
- 复用现成 `YlxwRF_TYPES` / `YlxwRF_DEFS` / `YlxwRF_SPECIAL`，零新增；
- 若只取 4 类，则每件仙品必有 3 条稀有战斗词条（密度过高，且期望值把封顶打爆）；
- 用 7 类时，单件仙品 3 条中**至少 1 条为稀有战斗词条的概率 = 1 − C(3,3)/C(7,3) = 97.1%**，几乎不会出现「仙品却零稀有词条」的落差（传说 2 条时该概率 85.7%，稀有 1 条时 57.1%）。
- 3 类百分比词条（锋芒/玄甲/长生）本就是「掉落装备以前拿不到的稀有属性」，纳入不违背需求（需求用「比如」列举，非穷举）。

> 若团队坚持「只发 4 类战斗稀有键」，只需把 `YlxwRF_TYPES` 换成 `["critRate","critDamage","dodgeRate","lifeLeech"]`，但需相应下调 `YlxwInnateK` 或条数，否则封顶会被打爆（见 §5）。

## 4. 注入点方案（伪代码）

### 4.1 新增生成函数（不改动任何 `YlxwRF_*` 既有函数）

```js
/* ★ R-141 天生稀有词条：境界因子表 + 品质条数表 + 折扣常数 */
var YlxwInnateRealmFactor = {
  "炼气期": 0.05, "筑基期": 0.10, "金丹期": 0.20, "元婴期": 0.35,
  "化神期": 0.55, "合道期": 0.80, "长生境": 1.00
};
var YlxwInnateCount = { "普通": 0, "稀有": 1, "传说": 2, "仙品": 3 };
var YlxwInnateK = 0.35;

/* 生成天生词条；realm 为境界名（如 "长生境"）。无法定位境界 ⇒ 返回 []（不发词条） */
function YlxwInnate_Roll(rarity, realm) {
  var n = YlxwInnateCount[rarity] || 0;
  if (n <= 0) return [];
  var R = YlxwInnateRealmFactor[realm];
  if (typeof R !== "number" || R <= 0) return [];
  var cfg = YlxwRF_Cfg(rarity);                 // 复用 YlxwRF_RARITY[rarity]（minV/maxV）
  var pool = YlxwRF_TYPES.slice(), chosen = [], i, idx, ty;
  for (i = 0; i < n && pool.length > 0; i++) {  // 同 YlxwRF_Roll：同一件内去重抽取
    idx = Math.floor(Math.random() * pool.length);
    chosen.push(pool[idx]); pool.splice(idx, 1);
  }
  return chosen.map(function (ty) {
    var d = YlxwRF_DEFS[ty] || {};
    var raw = (cfg.minV + Math.random() * (cfg.maxV - cfg.minV))
            * (YlxwRF_SPECIAL[ty] || 1) * R * YlxwInnateK;
    return { type: ty, name: d.name || ty, value: Math.round(raw * 1000) / 1000, src: "innate" };
  });
}
```

- 复用 `YlxwRF_Cfg` / `YlxwRF_TYPES` / `YlxwRF_DEFS` / `YlxwRF_SPECIAL`，**不修改**洗炼逻辑；
- 词条带 `src:"innate"` 标记，便于 UI 区分「天生」与「洗炼」；
- 数值三位小数，与洗炼完全同构（`YlxwBattleBonus` 直接可用）。

### 4.2 注入点：`vs()` 授予管道（**唯一入口**）

在 `vs(t, r, a=1, l)` 的 `if(b){ ... }`（`b = isEquippable`）分支内、**去重判断之前**：

```js
if (b) {                                  // isEquippable
  const _m2 = /^\[(.+?)\]/.exec(d || "");
  if (_m2) { r = {...r, realm:_m2[1], realmRequirement:_m2[1]}; delete r.minRealm }

  /* ★ R-141：天生词条（幂等；spec 已带则沿用，避免重复 roll） */
  const _inn = (r.innateAffixes && r.innateAffixes.length)
    ? r.innateAffixes
    : YlxwInnate_Roll(v, (l && l.realm) || r.realm);
  const _innKey = _inn.length ? JSON.stringify(_inn) : "";

  const K = c.findIndex(h =>
    h.isEquippable && h.name === d && h.rarity === v && (h.level||0) === (r.level||0)
    && (h.equipmentSlot||"") === (S||"")
    && (h.advancedItemType||"") === (r.advancedItemType||"")
    && (h.advancedItemId||"")   === (r.advancedItemId||"")
    && (h.reviveChances||0)     === (r.reviveChances||0)
    && JSON.stringify(h.effect||{})          === JSON.stringify(T||{})
    && JSON.stringify(h.permanentEffect||{}) === JSON.stringify($||{})
    && JSON.stringify(h.innateAffixes||[])   === _innKey          /* ★ 新增：词条入堆叠键 */
  );
  if (K >= 0)
    return c[K] = {...c[K], effect:T, permanentEffect:$, realm:r.realm,
                   quantity:(c[K].quantity||1)+a}, c;

  for (let h = 0; h < a; h++)
    c.push({
      id: St(), name:d, type:j, description:r.description||"", quantity:1, rarity:v,
      level:r.level||0, effect:T, permanentEffect:$, isEquippable:!0, equipmentSlot:S,
      realm:r.realm, recipeData:r.recipeData, reviveChances:r.reviveChances,
      advancedItemType:r.advancedItemType, advancedItemId:r.advancedItemId,
      innateAffixes: _inn.length ? _inn.map(x => ({...x})) : void 0   /* ★ 新增：逐件深拷贝 */
    });
  return c;
}
```

**要点**：
1. **幂等**：`r.innateAffixes` 已存在则沿用，杜绝「同一件物品被多次授予时重复 roll / 词条漂移」。
2. **境界来源 = `l.realm`（玩家/上下文境界）**，与同函数内 `ry(T,$,l.realm,l.realmLevel,...)` 的缩放口径**完全一致** ⇒ 天生词条与装备基础数值**同步按境界缩放**，不会出现「装备数值是长生级、词条却是炼气级」的错配。
3. **`innateAffixes` 进入堆叠键**：天生词条是随机值，两件同名同品质装备若词条不同则**不合并**（避免合并时丢词条）。由于**普通品质天生 0 条**，占掉落大头的普通装备仍正常堆叠，背包膨胀有限。
4. 多件（`a>1`）时逐件深拷贝，避免共享同一数组引用。

### 4.3 为什么不用 `cy()`（重要）

- `cy()` 里的 `x.innateAffixes` 会在物品被 `vs()` 领取时**被字段重建丢弃**（`vs` 的 push 列表是白名单，不 spread `r`）；
- `cy()` 覆盖不到历练/秘境主掉落 `_y()`；
- 因此**只注入 `vs()` 一处**即可覆盖：历练、秘境、抽奖领取、任务/邮件/活动奖励、**商店购买**（商店购买也走 `vs`：`const C=vs(N.inventory,R,E,{realm:N.realm,realmLevel:N.realmLevel})`）。

> ⚠ 副作用：商店**购买**的装备也会天生带词条（因为购买走 `vs`）。若团队认为商店装备不应带词条，需在 `vs` 里增加「来源标记」参数区分（见 §12 待拍板）。

### 4.4 消费层：2 处聚合函数各加一段（新增字段读取）

**`YlxwBattleBonus(p)` @1316967 —— 装备层循环（原仅读 `reforgeAffixes`）：**

```js
var eq = YlxwEqItems(p), i, j, af;
for (i = 0; i < eq.length; i++) {
  if (!eq[i]) continue;
  var affs = (eq[i].reforgeAffixes || []).concat(eq[i].innateAffixes || []);  /* ★ 合并两源 */
  for (j = 0; j < affs.length; j++) {
    af = affs[j];
    if (!af || !af.value) continue;
    if (af.type === "critRate" || af.type === "critDamage"
     || af.type === "dodgeRate" || af.type === "lifeLeech") {
      o[af.type] += af.value;
    }
  }
}
/* 末尾 YlxwBattleCap(o) 原样保留 —— 封顶语义不变 */
```

**`YlxwStatExtras(p, r)` @7505 —— 装备层循环（原仅读 `reforgeAffixes`）：**

```js
for (i = 0; i < eq.length; i++) {
  it = eq[i];
  if (!it) continue;
  var affs = (it.reforgeAffixes || []).concat(it.innateAffixes || []);       /* ★ 合并两源 */
  for (j = 0; j < affs.length; j++) {
    af = affs[j];
    if (!af || !af.value) continue;
    if (af.type === "attackPercent")       r.attack  += Math.floor(p.attack  * af.value);
    else if (af.type === "defensePercent") r.defense += Math.floor(p.defense * af.value);
    else if (af.type === "hpPercent")      r.maxHp   += Math.floor(p.maxHp   * af.value);
  }
}
```

> 这两处是**聚合层的字段读取扩展**，**不触碰**战斗核心公式（`F = 0.1 + 速度占比×0.1 + critRate` / `X = round(Z × (1.5 + critDamage))` / 吸血回血分支），符合红线。

### 4.5 是否区分「天生词条」与「洗炼词条」两个字段？

**结论：区分，用独立字段 `innateAffixes`（推荐）**，而非复用 `reforgeAffixes`。

| 方案 | 消费层改动 | 洗炼交互 | 结论 |
|---|---|---|---|
| A. 复用 `reforgeAffixes` | 0 处 | `YlxwRF_Apply` 用 `pendingReforge` **整体覆盖** ⇒ 天生词条被洗掉；且 `YlxwRF_ToggleLock` 不允许全锁 ⇒ 无法保全 | ❌ 玩家一洗就丢，落差大 |
| **B. 独立 `innateAffixes`（推荐）** | 2 处（§4.4） | 洗炼只动 `reforgeAffixes`，天生词条**永久保留**；两源在消费层相加 | ✅ 洗炼不毁天生，且天生强度仅洗炼 1/3，不喧宾夺主 |

独立字段的额外好处：天生词条可单独封顶/统计/展示，且 `祭炼/融合` 的现有逻辑（spread 保留 / 重建丢弃）行为天然正确（见 §6）。

## 5. 封顶校验（满配算例）

### 5.1 各来源上限（来自基线实测）

| 来源 | 暴击率 | 暴伤 | 闪避 | 吸血 | 减伤 |
|---|---|---|---|---|---|
| 羁绊 `YlxwBondCapCfg` @9033 | 0.15 | 0.40 | 0.15 | 0.10 | 0.20 |
| 妖灵灵纹（任选 1 条，`R018B_RUNE_TABLE`） | 0.015 | — | 0.015 | 0.01 | 0.02 |
| 自创神通 `YlxwSP_CAP` @10180 | 0.15 | 0.50 | 0.15 | 0.10 | 0.20 |
| **装备（R-141 新增，见下）** | 见下 | 见下 | 见下 | 见下 | 0（本方案不产减伤） |
| **统一封顶 `YlxwBattleCapCfg`** | **0.35** | **1.00** | **0.35** | **0.25** | 0.50 |

### 5.2 装备层贡献（长生境，满 15 件仙品）

**装备槽上限**（`ce` 枚举 + 匹配表 `Jt`）：武器 1 + 护甲 6（头/肩/胸/手/腿/靴）+ 戒指 4 + 首饰 2 + 法宝 2 = **≤15 件**。
每件仙品 3 条 ⇒ 共 45 条；7 类均匀 ⇒ **每类期望 45/7 = 6.43 条**；单件内同类去重 ⇒ **单类单件 ≤1 条**。

**期望贡献**（`F = 0.35`，仙品均值 0.17）：

| 词条 | 单条均值 | 期望条数 | 期望合计 |
|---|---|---|---|
| 暴击率 | 0.17×0.35×0.35 = 0.020825 | 6.43 | **+13.4%** |
| 暴伤 | 0.17×0.50×0.35 = 0.029750 | 6.43 | **+19.1%** |
| 闪避 | 0.17×0.30×0.35 = 0.017850 | 6.43 | **+11.5%** |
| 吸血 | 0.17×0.25×0.35 = 0.014875 | 6.43 | **+9.6%** |

**绝对上限**（15 件全部命中同一词条，单件 ≤1 条）：

| 词条 | 单条上限 | ×15 | 装备层绝对上限 |
|---|---|---|---|
| 暴击率 | 0.02695 | 15 | 0.404 |
| 暴伤 | 0.03850 | 15 | 0.578 |
| 闪避 | 0.02310 | 15 | 0.347 |
| 吸血 | 0.01925 | 15 | 0.289 |

### 5.3 满配总账（长生境：装备期望 + 羁绊满 + 灵纹 + 神通满）

| 词条 | 装备(期望) | 羁绊 | 灵纹 | 神通 | **合计** | 封顶 | 结论 |
|---|---|---|---|---|---|---|---|
| 暴击率 | 0.134 | 0.15 | 0.015 | 0.15 | **0.449** | 0.35 | 超 0.099 → 钳制 |
| 暴伤 | 0.191 | 0.40 | — | 0.50 | **1.091** | 1.00 | 超 0.091 → 钳制 |
| 闪避 | 0.115 | 0.15 | 0.015 | 0.15 | **0.430** | 0.35 | 超 0.080 → 钳制 |
| 吸血 | 0.096 | 0.10 | 0.01 | 0.10 | **0.306** | 0.25 | 超 0.056 → 钳制 |

**结论与判读**：

1. **封顶不可能被"突破"** —— `YlxwBattleCap` 在 `YlxwBattleBonus` 末尾统一钳制，且战斗内 `W = clamp(0.1 + 速度占比×0.1 + critRate, 0, 0.35)` 二次钳制暴击率。**红线（不得突破封顶语义）成立。**
2. **但满配会"顶到"上限** —— 原因是**非装备来源（羁绊+灵纹+神通）本身已占封顶的 84%–90%**（见下表），这是**基线既有事实**，与 R-141 无关：

   | 词条 | 羁绊+灵纹+神通（无装备） | 占封顶 |
   |---|---|---|
   | 暴击率 | 0.315 | 90% |
   | 暴伤 | 0.900 | 90% |
   | 闪避 | 0.315 | 90% |
   | 吸血 | 0.210 | 84% |

3. **因此 R-141 的定位**：装备天生词条在**中前期（筑基–化神）**是实打实的战力增量；到**满配终局**则被钳制为"补最后一脚"。这是**可接受的**——装备词条不会破坏封顶，只是终局边际收益递减。
4. **额外收口**：战斗暴击率公式自带 `0.1 + 速度占比×0.1` 基础值，实际留给「暴击率加成」的空间只有 0.15–0.25，比 0.35 的表面上限更紧 ⇒ 装备暴击词条的终局边际收益进一步递减，风险更低。
5. 若团队希望**装备在终局仍是有效杠杆**，需下调羁绊/神通上限（**超出 R-141 范围**，见 §12 待拍板）。

### 5.4 中前期算例（元婴境，满 15 件仙品）

`F = 0.35 × 0.35 = 0.1225`，每类期望 6.43 条：

| 词条 | 期望合计（元婴·满仙品） |
|---|---|
| 暴击率 | +4.7% |
| 暴伤 | +6.7% |
| 闪避 | +4.0% |
| 吸血 | +3.4% |

叠加**部分**羁绊/神通（远未满），元婴玩家可感知但不失衡。

## 8. 可选项（不做也行，列出利弊）

### 选项 A：修复 `player.critRate/dodgeRate/lifeLeech` 死字段

- **现状**：灵田稀有草把 `player.critRate/dodgeRate/lifeLeech` 写入存档（服务端 `srv/index_v28.ts` 8453–8456），但客户端**从不读取这三个玩家字段进战斗** —— 死字段。
- **做法**：在 `YlxwBattleBonus` 中追加 `o.critRate += p.critRate||0` 等三行。
- **利**：灵田稀有草终于生效，闭环；与 R-141 同属"稀有属性"线，可一并验收。
- **弊**：新增一条独立加成来源，**未纳入本方案的封顶预算**（灵田草 cap：`FARM_CROP_ATTR_CAP = {hitRate:8, critRate:8, dodgeRate:6, lifeLeech:4}`，单位百分点 ⇒ 最多 +8%/+6%/+4%）；会让满配更容易顶到封顶；且属于 R-141 之外的系统，扩大回归面。
- **建议**：**本轮不做**，作为 R-141 的独立后续需求登记。

### 选项 B：给回合制技能 `zy` 补吸血分支

- **现状**：回合制**普攻 `km`** 有 `G && X>0 && lifeLeech>0 → 回血 floor(X×lifeLeech)`；**技能 `zy` 没有吸血分支** ⇒ 技能伤害不吸血。
- **做法**：在 `zy` 的伤害结算后复制 `km` 的吸血逻辑。
- **利**：吸血词条在技能流打法下才真正可用；否则 R-141 的吸血词条收益打对折。
- **弊**：触碰战斗结算函数（虽非核心公式，但属战斗引擎），回归面较大；需重新做战斗数值回归。
- **建议**：**列为强推荐的可选项**，但**与 R-141 分包上线**（R-141 先发，吸血在普攻已可用；技能吸血单独一版）。

## 11. 验收要点（供测试）

1. **品质门槛**：普通装备 `innateAffixes` 必为 `undefined`；稀有=1 / 传说=2 / 仙品=3 条。
2. **境界单调**：同一件仙品，境界越高，单条词条数值越大；炼气 < 筑基 < … < 长生，且长生/炼气 = 20×。
3. **同件去重**：同一件装备内 `type` 不重复。
4. **消费生效**：装备一件长生仙品（含暴击词条）后，角色面板暴击率上升；快速战斗与回合制战斗均生效。
5. **封顶**：构造满配玩家，面板五格均 ≤ `YlxwBattleCapCfg`。
6. **洗炼不毁天生**：洗炼后 `innateAffixes` 原样保留。
7. **祭炼保留**：祭炼后 `innateAffixes` 原样保留且数值不变。
8. **融合**：融合结果无 `innateAffixes`（预期行为）。
9. **老存档**：加载 0.9.16 存档不报错，老装备 `innateAffixes` 为空。
