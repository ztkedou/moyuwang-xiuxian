## 2. 按功能分组的改动清单

### 2.1 新增表 / 索引

**`market_payouts`**（`1ec1b63:server/index.ts:143-152`）——交易行卖家收益托管表：

```sql
CREATE TABLE IF NOT EXISTS market_payouts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL,      -- 卖家
  listing_id INTEGER,            -- 关联商品
  amount INTEGER NOT NULL,       -- 待领取灵石
  claimed INTEGER NOT NULL DEFAULT 0,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users (id)
);
```

配套索引：`idx_payouts_user ON market_payouts(user_id, claimed)`（`:153`）。

设计意图（源码注释，`:140`）：**「物品售出后，卖家灵石先入账到此表，待卖家客户端领取」**——即把「卖家收款」从「买卖双方各自客户端改数」改为「服务端托管 + 显式领取」。

## 4. 会话 / 存档机制冲突判定（重点）

### 4.1 上游的「会话隔离修复」是什么

**纯客户端，零服务端改动。** 上游 HEAD 改了两个客户端文件：

- `services/cloudSaveService.ts`（135 行改动，`1ec1b63:services/cloudSaveService.ts`）：
  - 新增 `const STALE_REQUEST_MSG = 'Session changed, request aborted'`；
  - 新增 `assertSession(sessionId)`——比较 `useAuthStore.getState().sessionId`，不等就抛错；
  - `refreshAccessToken(sessionId)` / `fetchWithAuth(url, options, sessionId)` 全程带 `sessionId` 参数，在每个 `await` 前后 `assertSession`；
  - 401 处理新增判断：**「另一请求可能已刷新当前会话的 token，直接用新 token 重试」**；
  - 关键注释（`:89`）：**「旧 token 的迟到响应不能让已成功刷新的当前会话登出」**。
- `hooks/useAutoCloudSave.ts`（3 行）：轮询前取 `sessionId`、无 token 直接 return；catch 里 `if (useAuthStore.getState().sessionId !== sessionId) return;`——**旧会话的报错不弹给新会话**。

一句话：上游修的是**客户端竞态**——旧登录会话的在途响应/401/报错，不得污染或登出刚登录的新会话。

### 4.2 我们的机制是什么

**服务端权威，多层锁。**（全部在 `srv/index_v26l_b.ts`）

| 层 | 实现 | 位置 |
|---|---|---|
| 单写者会话锁 | `active_sessions` 表 + `/api/session/claim`（UUID，带 `superseded` 顶号语义）/ `heartbeat`（60s 续期）/ `state` | `:1672-1719` |
| 写归属校验 | `/api/save` 校验 `X-YL-Session`，不匹配 → `409 session_superseded`；**头缺失则放行**（兼容老客户端/GM） | `:1721-1733` |
| 防倒滚 | `/api/save` 强制 `X-YL-Base-Revision`，落后当前 `gm_revision` 或缺失 → `409 stale_save` 并回吐云端现档 | `:1764-1775` |
| 读改写互斥 | `saveLocks` Map + `withSaveLock` | `:1002`、`:1744` |
| 权威结算 | `settleSaveEconV2` 离线重算封顶 + 计数器配额 + 总额兜底 | `:1568`、`:1780` |
| 修订号 | `gm_revision` 单调递增，响应回传供客户端回填 base | `:1785`、`:1801` |
| 快照 | `save_snapshots` 写前节流快照 | `:1664` |

我们的**客户端**（`build/assets/index-v26m-20260927.js`）已完整接入：`X-YL-Session` ×2、`X-YL-Base-Revision` ×2、`session/claim` ×1、`session/heartbeat` ×1、`settledExp` ×1。

### 4.3 判定：**不冲突，但有两个真实陷阱**

**层次不同，互补**：上游 = 客户端「防旧会话污染新会话」的状态机守卫；我们 = 服务端「单写者 + 乐观锁 + 防倒滚」的权威约束。二者可以并存。

**陷阱 ①：同名 `sessionId`，语义完全不同。**
- 上游的 `sessionId` = `authStore` 里的**客户端登录计数器**（整数，每次登录 +1）；
- 我们的 `sessionId` = 服务端 `/api/session/claim` 下发的 **UUID**，用于 `X-YL-Session` 头。
- 我们的客户端 bundle 里 `sessionId` 已出现 2 次（我们自己的实现）。**若把上游客户端代码整份合并，两个 `sessionId` 会互相覆盖语义。**

**陷阱 ②：整份替换上游客户端存档代码 = 灾难。**
上游 `cloudSaveService.pushSave` **不带** `X-YL-Session`，**也不带** `X-YL-Base-Revision`，且不消费响应里的 `gm_revision`。而我们的服务端对「`saves` 行已存在」的 `/api/save` **强制要求** `X-YL-Base-Revision`（`:1770`，缺失即 `409 stale_save`）。因此：

> **整份替换上游 `cloudSaveService.ts` ⇒ 所有非首次存档全部 409。**

必须**外科手术式**合并：只吸收「旧会话迟到响应不得登出/污染新会话」的**守卫思路**，保留我们的 `X-YL-Session` / `X-YL-Base-Revision` 头部注入与 `gm_revision` 回填。

### 4.4 该吸收的点

| 上游思路 | 我们是否需要 | 理由 |
|---|---|---|
| `assertSession` 守卫（await 前后校验会话未变） | ✅ 值得吸收 | 我们客户端目前只在服务端侧防顶号；客户端侧「旧会话迟到响应」仍可能覆盖 store。这是**与我们的锁正交的一层**。 |
| 401 时「token 已被本会话刷新则直接重试，不重复刷新」 | ✅ 值得吸收 | 避免 refresh 抖动。 |
| `useAutoCloudSave` 旧会话静默丢弃错误 toast | ✅ 值得吸收 | 纯体验优化，零风险。 |
| 用 `authStore.sessionId` 整数计数器做会话标识 | ❌ 不要照搬 | 与我们服务端 UUID 会话冲突；应用我们的 `X-YL-Session` 值。 |
| 整份替换 `cloudSaveService.ts` | ❌ 绝对不要 | 见陷阱 ②。 |

## 6. 分档建议

### 🟢 A 档：低风险，可直接摘出来合并（纯服务端、彼此独立）

| 项 | 工作量 | 说明 |
|---|---|---|
| `sellerId: r.seller_id` | 1 行 | `index_v26l_b.ts:3032`；SELECT 已含 `seller_id`（`:3008`） |

| `catch (e)` → `catch` | 噪音 | 可随其它改动顺带 |
| `market_payouts` 表 + 索引 | ~15 行 DDL | 需放在既有 `db.serialize`/`CREATE TABLE` 建表块内（我们建表在 `:186` 一带，参照 `market_listings`） |

### 🟡 B 档：必须跟客户端一起动（服务端 + 客户端联动）

| 项 | 为什么必须联动 |
|---|---|
