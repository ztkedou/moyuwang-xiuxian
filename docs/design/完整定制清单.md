## 3. 为什么压缩层 diff 不可靠（技术结论）

我们尝试过「用上游基线构建产物与线上 bundle 做锚点对齐」，结果：

- 最长公共段匹配率仅 **66.92%**
- 原因：**esbuild 的压缩变量名是全局分配的**。我们的补丁新增了约 118KB 代码，导致 React 内部的变量名从 `k/G/Z/te/j/A/N` 整体重排成 `E/G/Z/te/N/M/$/k`。
- 结论：**只要改动了任何代码，压缩产物的标识符会全局漂移**，无法用「压缩层 diff」还原出精确的改动点。
- 唯一可靠的压缩层信号是：**字符串字面量**（不受混淆影响）与 **CSS 类名**。本报告的清单即基于这两者 + 我们自己的脚本记录。

## 4. 三条可行路线

### 路线 A：找到那份源码树，做真正的三方合并（唯一「无损」路径）
1. 拿到用户改过的源码（或从压缩产物逆向重建全部定制）
2. `git remote add upstream` → 合并 `b822f2d..1ec1b63`
3. 解决冲突（预计集中在 `LogPanel`、`GameHeader`、`SettingsModal`、`ChangelogModal`、`useVersionCheck`、`cloudSaveService`、`useAutoCloudSave`、`authStore`）
4. 重新配置 `VITE_API_BASE_URL=/yl/api`、`VITE_APP_VERSION`，`vite build`
5. 部署 + 全量回归验收

**前提**：必须先拿到源码。否则第 1 步等价于「把 118KB 压缩代码人工还原成源码」，工作量与风险都不可接受。

### 路线 B：不重建，只合并能安全摘取的上游改动
- **服务端**：上游 0.3.8 对 `server/index.ts` 的改动**很小**（交易行 +2 端点 +1 表 +3 helper），可直接合并进我们的 9,001 行服务端 → 低风险
- **客户端**：
  - ✅ 可摘：emoji 文案优化、交易行/售卖结算修复、溢出经验的**数据层**（新字段 `storedExp`）
  - ⚠️ 需要一起动：会话隔离修复（与我们 v26i 改了同一批函数体）
  - ❌ 摘不到：九天通天塔 / 自创神通 / 装备洗炼 / 灵兽远征（约 2,500 行新代码 + 代码分割）

### 路线 C：只重建客户端，接受定制需逐条重做
- 用上游 HEAD 源码构建，把 1.A / 1.B 的定制在源码层重做
- 工作量集中在 1.A（用户侧 12 项，**无源码无文档**，需逆向压缩代码）
