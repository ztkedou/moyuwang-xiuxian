## 2. 前提不成立之处与修正路线

### 2.1 原方案行不通的三点

1. **"在线打坐/历练灵石 ×2"无法实现。** 现有引擎的倍率只在服务端结算点（离线/灵田/炼丹）生效；在线收益在客户端混淆码内结算，服务端看不到、也改不动。要真做"在线 ×2"必须改客户端混淆码——与本活动"零客户端改动"的目标冲突。
2. **没有活动结算定时器。** `setInterval` 只有限流桶清理一个，必须新建。
3. **`minutes` 可被伪造。** 策划文档称"口径用 minutes，天然防自激、不可伪造"——**防自激成立**（奖励加灵石，不加 playTime），**但"不可伪造"不成立**（playTime 是客户端字段）。

### 2.2 修正路线（本文采纳）

**保持"零客户端改动、奖励随境界缩放、按在线时长发放"三个目标，改为：**

- 玩家侧效果：活动窗口内**在线每满 1 小时，收到一封附灵石的邮件**（等效于"在线收益额外 +1 小时份"）。
- 数据口径：`stats_daily.minutes` 差值（防自激）+ **服务端 `saves.updated_at` 活跃度**（在线门禁，服务端权威）+ **相邻 tick 的真实墙钟时长**（上限钳制，抵消 playTime 伪造）。
- 发奖路径：`insertMail()` → 玩家在既有邮箱 UI 点"领取" → `mailClaimCore` → `updatePlayerSave` 入账（**不经经济钳制**）。
- 活动展示：复用既有 `events` 表 + 新增类型 `stones2_live`（仅展示，**不参与任何倍率计算**），客户端既有"限时活动（只读）"面板自动显示，**无需改客户端**。

> 若要**字面意义的在线 ×2**，唯一路径是改客户端混淆码（`RS.handleMeditate` 等），属于另一个量级的工作，本文不覆盖。

```ts
// [raincore] Y21-R "Tianjiang Lingyu" pure logic core (no external refs; extractable for unit tests).
// 口径：以 stats_daily.minutes 差值（客户端在线代理）为基准，用"相邻 tick 真实墙钟分钟数"封顶
//       （服务端权威，抵消 playTime 伪造），用 saves.updated_at 活跃度做在线门禁。
// 数值：时薪是**派生量**，由客户端打坐循环实测推出（推导见 §7.1）：
//   stones/hour = 17676 * rainRealmFactor(idx);  17676 = round(0.982 * 5 * 3600)
//   rainRealmFactor(i) = i <= 0 ? 4/3 : 2i + 1
const RAIN_HOURLY_STONES_BASE = 17676;        // = round(0.982 * 5 * 3600) = 4.91 石/秒 * 3600
const RAIN_SETTLE_MIN_MINUTES = 60;           // 满 1 小时才发
const RAIN_DAILY_CAP_MINUTES = 480;           // 单日结算上限 8h
const RAIN_ONLINE_STALE_MS = 15 * 60 * 1000;  // 在线门禁：距上次存档 ≤15 分钟视为在线
const RAIN_TICK_MS = 10 * 60 * 1000;          // 结算周期 10 分钟
let rainEngineOn = false;   // activity_config.engine_on 的内存镜像（全局 kill switch；开机 + GM 路由同步）
let rainSettling = false;   // 重入保护：上一轮未跑完则跳过本轮
let rainLastTickMs = 0;     // 上一 tick 的服务端墙钟（硬上限来源）
// 境界系数（纯）：i<=0 → 4/3，否则 2i+1；NaN/负值钳 0
function rainRealmFactor(idx: unknown): number {
  const i = Math.max(0, Math.floor(Number(idx) || 0));
  return i <= 0 ? 4 / 3 : 2 * i + 1;
}
// 境界时薪（纯）
function rainHourlyStones(idx: unknown): number {
  return Math.floor(RAIN_HOURLY_STONES_BASE * rainRealmFactor(idx));
}
// 本 tick 可计入的在线分钟（纯）：minutes 差值被"墙钟分钟"封顶（防 playTime 伪造）；负差/NaN 归 0
function rainDeltaMinutes(prevMinutes: unknown, nowMinutes: unknown, wallMinutes: unknown): number {
  const p = Math.max(0, Math.floor(Number(prevMinutes) || 0));
  const n = Math.max(0, Math.floor(Number(nowMinutes) || 0));
  const raw = n > p ? n - p : 0;
  const cap = Math.max(1, Math.ceil(Math.max(0, Number(wallMinutes) || 0)));
  return Math.min(raw, cap);
}
// 本 tick 可发放的小时数（纯）：受"未发零头"与"单日上限"双重约束，向下取整
function rainPayableHours(accruedMinutes: unknown, settledMinutes: unknown): number {
  const acc = Math.max(0, Math.floor(Number(accruedMinutes) || 0));
  const done = Math.max(0, Math.floor(Number(settledMinutes) || 0));
  const room = Math.max(0, RAIN_DAILY_CAP_MINUTES - done);
  return Math.floor(Math.min(acc, room) / RAIN_SETTLE_MIN_MINUTES);
}
// 奖励灵石（纯）：小时数 × 境界时薪
function rainBonusStones(hours: unknown, idx: unknown): number {
  const h = Math.max(0, Math.floor(Number(hours) || 0));
  return h * rainHourlyStones(idx);
}
```

```ts
              SET last_minutes = ?, accrued_minutes = accrued_minutes + ? - ?, settled_minutes = settled_minutes + ?, updated_at = CURRENT_TIMESTAMP
            WHERE player_id = ? AND event_id = ? AND date = ? AND settled_minutes + ? <= ?`,
          [nowMinutes, delta, payMinutes, payMinutes, uid, eventId, today, payMinutes, RAIN_DAILY_CAP_MINUTES]
        );
        if (!claim.changes) continue; // 未占住（并发/超上限），下轮再试
        // 4) 发邮件（境界取服务端 rankings.realm_index）
        const bonus = rainBonusStones(hours, row.ri);
        try {
          await insertMail(
            uid,
            '天降灵雨 · 在线修行回馈',
            `灵雨润泽，道友在线修行 ${hours} 小时，天地灵气化作灵石相赠：\n\n· 灵石 +${bonus}（请点击下方领取）\n\n（活动期间在线每满 1 小时结算一次，单日上限 8 小时）`,
            'system',
            bonus
          );
        } catch (mailErr: any) {
          // 补偿：邮件失败 → 回退本次占位，玩家下轮可重试（全或无，同 mailClaimCore 纪律）
          await dbRun(
            `UPDATE activity_rain_state
                SET accrued_minutes = accrued_minutes + ?, settled_minutes = settled_minutes - ?
              WHERE player_id = ? AND event_id = ? AND date = ?`,
            [payMinutes, payMinutes, uid, eventId, today]
          ).catch(() => {});
          console.error('rain mail error:', mailErr?.message || mailErr);
        }
      } catch (perUserErr: any) {
        console.error('rain settle per-user error:', perUserErr?.message || perUserErr); // 单玩家失败不影响整轮
      }
    }
  } catch (e: any) {
    console.error('rain settle tick error:', e?.message || e); // 数据库异常：不发奖、不崩
  } finally {
    rainSettling = false;
  }
}
setInterval(() => { rainSettleTick().catch((e: any) => console.error('rain tick error:', e?.message || e)); }, RAIN_TICK_MS).unref();
```

> **启动即跑一轮**（可选）：在 `setInterval` 之后加 `rainSettleTick().catch(() => {});`，避免首次结算等待 10 分钟。

## 4. 防刷与边界情况

### 4.1 防刷设计（四层）

| 层 | 机制 | 实现位置 |
|---|---|---|
| ① 口径不自激 | 奖励发放只加灵石，**不加 playTime**；下一轮 `minutes` 差值不受本次奖励影响 | `computeStatsDeltas`（`index.ts:3481`）只读 `playTime` |
| ② 墙钟封顶 | 每 tick 计入分钟数 ≤ `ceil(墙钟分钟)`（tick 间隔 10min → 每轮最多 10 分钟）。伪造 `playTime` 撑大 `minutes` 无效，只能拿到与真实在线时长同量级的奖励 | `rainDeltaMinutes()`（改动③） |
| ③ 幂等键 | `PRIMARY KEY(player_id, event_id, date)`；发放用守卫式单语句 `UPDATE ... WHERE settled_minutes + ? <= 480`，`changes=0` 即放弃 | `activity_rain_state`（改动①）、改动④步骤 3 |
| ④ 单日上限 + 最小粒度 | 单日结算 ≤ 480 分钟（8h，= 时薪×8）；不足 60 分钟不发，零头结转 | `RAIN_DAILY_CAP_MINUTES`/`RAIN_SETTLE_MIN_MINUTES`（改动③） |

> 注：`minutes` 本身可伪造，但被第②层墙钟封顶后，**伪造收益上限 = 真实在线时长对应的奖励**，无净收益，故无需再校验 `playTime` 本身。

### 4.2 边界情况

| 场景 | 行为 | 依据 |
|---|---|---|
| 活动未开启 / 无活跃场次 | 首个 `activity_config` 查询或 `events` 查询即 `return`，**零写入、零发奖** | 改动④步骤 0、1 |
| `engine_on='0'`（kill switch） | 同"未开启"，立即早退 | `index.ts:5646-5647` 同款语义 |
| 跨日（北京时间） | 状态按 `bjDate(nowMs)` 分日；跨日自然换行，单日上限随日重置 | `bjDate`（`index.ts:3347-3349`） |
| 玩家离线 | ① `saves.updated_at` 超 15 分钟 → 不进候选集；② `playTime` 不上涨 → `minutes` 差值为 0 | 改动④步骤 2；`index.ts:3481` |
| 玩家当日首次被扫到 | 只写基线 `last_minutes=当前值`，**不发奖**（防一次性把当天全量分钟入账） | 改动④"首见分支" |
| 数据库异常（查询/写入失败） | 整轮 `try/catch` 兜底，只记日志，**不发奖也不崩**；单玩家异常不影响整轮 | 改动④外层/内层 `catch` |
| 邮件发送失败 | 补偿式回退本次占位（`accrued` 加回、`settled` 减回），玩家下轮重试，**全或无** | 改动④步骤 4 补偿分支；对齐 `mailClaimCore`（`index.ts:4515-4518`） |
| 上一轮未跑完 | `rainSettling` 重入保护，跳过本轮，避免慢查询堆叠 | 改动④ |
| 境界缺失（无 rankings 行） | `row.ri` 为 null → `rainHourlyStones` 按炼气期（索引 0） | `rainHourlyStones()`（改动③） |
| 服务器重启 | 状态在 `activity_rain_state` 表内，重启不丢；`setInterval` 重新注册 | — |

### 4.3 回归风险：与经济钳制 `settleSaveEconV2` 的关系（重点）

**结论：本方案不触碰 `settleSaveEconV2` 的配额钳制，无回归风险。**

- `settleSaveEconV2` **只在 `POST /api/save` 内被调用一次**（`index.ts:1807`），用于钳制**客户端上传**的 `spiritStones`/`exp` 正增量。
- 本活动发奖走 `insertMail` → 玩家点 `/api/mail/claim` → `mailClaimCore` → `updatePlayerSave`（`index.ts:4544-4547`）。`updatePlayerSave` **不调用** `settleSaveEconV2`，因此**邮件入账不会被钳制**。
- 领取后服务器存档 `player.spiritStones` 已含奖励；客户端拉到新档（`gm_revision++` 触发刷新）后再上传时，服务端 `oldSd`（含奖励）与新档差值≈0，`capStone` 富余，**不会误判为异常增量**。
- 自激检查：`capStone` 依赖 `off.stones + dMed + dAdv + ... + sellAllow`，均与 `playTime`/邮件无关；奖励既不进 `stats_daily.silver_gain` 的正差，也不影响下轮 `minutes`。
- **唯一注意**：`/api/mail/claim` 有频控 `max:10/分钟`（`index.ts:4613`），每小时一封邮件不会触发。

## 7. 未确认项（明确列出不确定之处）

### 7.1 已消解（原为未确认，现已确认）

1. **「境界时薪」已确认——它是派生量，不是字面常量。** 实测自客户端打坐循环：
   ```
   每次打坐   = max(1, max(1, 境界序*2+1) + randInt(0..2) - 1) * 5
   有效频率   = 0.982 次/秒      （setCooldown(1) + 每秒 -1 冷却，40s 稳态实测）
   每秒收益   = 4.91 × rainRealmFactor(idx)
   时薪       = floor(17676 × rainRealmFactor(idx))     // 17676 = round(0.982 × 5 × 3600)
   rainRealmFactor(i) = i <= 0 ? 4/3 : 2i + 1
   ```
   验算 idx 0..6 → **23568 / 53028 / 88380 / 123732 / 159084 / 194436 / 229788**，与策划表逐位一致。
   **原判断"bundle 与源码中查无此数"本身成立，但结论错了**——它在代码里不是字面常量，所以搜索不到；正确做法是**按公式实现**。已在 `srv/index_activity.ts` 的 `[raincore]` 落地为 `RAIN_HOURLY_STONES_BASE`（=17676）+ `rainRealmFactor()`，天然随境界缩放，不再有"数值无锚点"问题。
2. **`/api/activity/list` 不存在——已确认。** 真实端点是 `GET /api/events`（`index.ts:5656-5699`），客户端 `YlxwTEvents` 正是调用它。§1 第 5 行、§5 的结论据此确认，无需再核。
3. **「活动引擎定时结算器」不存在——已确认。** 全文件唯一 `setInterval` 是限流桶清理（`index.ts:2676`）；现有引擎 `resolveEventMults`（`index.ts:5645`）是按请求的倍率解析器，不是定时器。本方案已新增结算器 `[raincore-settler]`。
4. **现有倍率管不到在线打坐——已确认。** 倍率只作用于服务端结算点（离线收益/灵田/炼丹），在线收益在客户端混淆码内（`index.ts:5780` 注释）。故本方案不追求"字面 ×2"，改为等效的"在线满 1 小时发 1 小时份"。

### 7.2 仍待确认

1. **"在线"的判定口径未与客户端对齐。** 本文用 `saves.updated_at ≤15min` 作服务端在线代理（同师徒系统 `MENTOR_ONLINE_MS` 口径，`index.ts:4223`）。若客户端存在"后台仍上传存档"的行为，可能把挂后台也算作在线；需产品确认是否可接受。
2. **`minutes` 的 1 分钟取整损耗。** `computeStatsDeltas` 每轮 `Math.floor(ms/60000)` 会丢弃 <1 分钟尾巴（`index.ts:3481`），多次上传会累计少计。本文用墙钟封顶后，实际入账分钟可能**略少于**真实在线时长（偏保守，不会多发）。
3. **未核实是否存在其它 `saves` 写入路径绕过 `updated_at` 更新。** 若某些后台任务直接改 `saves` 而不更新 `updated_at`，可能误判离线。仅确认了 `/api/save`、`updatePlayerSave`、离线领取、GM 路径均会刷新 `updated_at`（`index.ts:1048`、`1811`、`1834`）。
4. **未验证 `rankings.realm_index` 的实时性。** 境界取自 `rankings`（`index.ts:1104-1143`，随存档上传 upsert）。若玩家刚突破但尚未上传存档，结算时用的仍是旧境界，奖励可能滞后一档（偏保守）。
5. **并发/多进程假设。** 本方案假定服务端是**单进程单连接**（`node-sqlite3` 回调式，见 `index.ts:4514-4518` 注释）。若线上是多进程/多实例共享一个 DB，`rainSettling` 内存标志无效，幂等仅靠 `activity_rain_state` 的守卫式 `UPDATE`（仍安全，但可能多一次邮件尝试被 `settled` 上限挡下）。**多实例部署需复核。**
6. **`/api/events` 的频控与客户端轮询频率未测。** 客户端 `YlxwUseList("/events")` 的轮询周期未在本次核实范围内（`Mk=5e3` 常量出现在消息轮询处，是否用于 events 未确认）。
7. **活动展示的 `multiplier` 字段语义。** 客户端会显示"×2"（`YLXW_ACT` 或 `typeName` + `×` + multiplier），但本活动**并非真正的 ×2 收益**，而是"在线满 1 小时发 1 小时份"。**展示文案可能与实际机制不符**，建议产品确认是否要改文案（改文案需动客户端，或把 `multiplier` 设为 1 并靠 `name` 表达）。

按 `RAIN_DAILY_CAP_MINUTES = 480` 算，**单玩家每天最多 8 条**。而 `chronicle` 表上线时只有 31 行
（正常一天 5~10 条），会被彻底刷屏。

**为什么不能简单地传 `lingshi = 0`**：灵雨的灵石**不是直接入档**，而是走邮件附件领取 ——
`mailClaimCore`（`v27a:4740`）读 `attached_lingshi` 再加进 `player.spiritStones`（`v27a:4767`）。
传 0 会让「该邮件没有可领取附件」（`v27a:4754`），**奖励直接发不出去**。

**既有约定（判断「该不该广播」的口径）**：鸿函广播是留给**稀有、玩家主动获得的大额奖励**的 ——
`成就达成奖励`（`v27a:7862`，真实 `stones`）入志、`好友赠丹`（`v27a:6529`）入志；
而 `闭关修炼 · 离线收益`（`v27a:7780`）因为**奖励已直接入档、邮件只是回执**，传的是 `lingshi = 0`，天然不入志。
灵雨属**自动、周期性、人人都有**的例行收益，**不属于「稀有」** ⇒ 不该广播。

### 8.2 GM 审计流水会永久留下旧名（**故意不改**）
