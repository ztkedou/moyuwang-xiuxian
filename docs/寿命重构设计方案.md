# yl 寿命系统重构 · 设计方案（v2，待确认）

基线：线上 0.9.60，客户端 `build/assets/index-v2960-20261011.js`（2,174,244 字符），服务端 `srv/index_v28.ts`。

## 0. 一句话

把「剩余寿命递减」翻转成「年龄递增」；死线由**建号时抽定的隐藏比例**决定，随境界增长自动落在展示区间内；面板只展示区间；打坐/历练/离线从扣寿命改为涨年龄；寿终即清档重开。

## 1. 核心模型

### 1.1 三个存储字段

| 字段 | 含义 | 可见性 |
|---|---|---|
| `age` | 当前年龄（内部小数，面板取整） | 可见 |
| `lifeRatio` | **建号时随机抽定**的比例 ∈ [0.9, 1]，终身不变 | **隐藏** |
| `lifeBonus` | 丹药/装备的永久加寿累计 | 间接可见 |

### 1.2 三个派生量

```
U_base(realm, lv) = 100 + growth(realm, lv)          ← 境界决定的「基准上限」
U_display         = U_base + lifeBonus                ← 面板展示的区间上限
deathLine         = lifeRatio × U_base + lifeBonus    ← 真实死线（隐藏）
展示区间           = [ floor(0.9 × U_display), floor(U_display) ]
寿终条件           = age >= deathLine
```

### 1.3 为什么用「固定比例」而不是「固定偏移」

`lifeRatio` 是**比例**而非年数。这样：

- 建号时 `U_base = 100`，`deathLine = lifeRatio × 100 ∈ [90, 100]`，展示 `[90, 100]` ✓
- 筑基 1 层 `U_base = 200`，`deathLine = lifeRatio × 200 ∈ [180, 200]`，展示 `[180, 200]` ✓
- 金丹 1 层 `U_base = 450`，`deathLine ∈ [405, 450]`，展示 `[405, 450]` ✓

**数学自洽性（已验算）**：对任意 `lifeBonus ≥ 0`、`lifeRatio ∈ [0.9, 1]`，

```
0.9 × U_display  ≤  deathLine  ≤  U_display
```

恒成立 ⇒ **真实死线永远落在展示区间内，永不穿帮**（证明：左端 ⟺ `(0.9 − lifeRatio)×U_base ≤ 0.1×lifeBonus`，因 `lifeRatio ≥ 0.9` 左端 ≤ 0；右端 ⟺ `lifeRatio ≤ 1`）。

若改用「固定偏移」模型，区间宽度会恒为 10 年，长生境变成「7990–8000 岁」，与你要的「长生 7200–8000」不符。所以必须用比例模型。

### 1.4 旧字段 `lifespan` 整体废除

`player.lifespan`（当前剩余寿命）**全部替换为 `player.age`**。

## 2. 数值体系

### 2.1 区间上限（沿用你第 5 条指定的《凡人修仙传》设定，不动）

`Cs[realm].baseMaxLifespan` = `[100, 200, 450, 1000, 2000, 4000, 8000]`，对应炼气/筑基/金丹/元婴/化神/合道/长生。

### 2.2 成长公式：**沿用现有 `YlxwLifeStep`，一行不改**

```js
var cur = YLXW_LIFE_TBL[i], nxt = YLXW_LIFE_NEXT[i], half = (nxt - cur) * 0.5;
return big ? half : half / 8;
```

- 小境界（1→9 层）：`(next − cur) / 16`
- 大境界突破：`(next − cur) / 2`

**数学自洽性（已验算）**：小境界 8 步 + 大境界 1 步 = `8×(d/16) + d/2 = d`，恰好等于上下限之差。所以

```
炼气1层 U=100 → 炼气9层 U=150 → 筑基1层 U=200   （100 完全补齐）
筑基1层 U=200 → 筑基9层 U=325 → 金丹1层 U=450   （250 完全补齐）
```

⇒ **你要的「前 9 层少量增加，跨大境界大量补齐」，现有公式已经完全满足，无需重新设计步长。**

### 2.3 完整区间表（`U = 100 + growth`，展示区间 = `[⌊0.9U⌋, ⌊U⌋]`）

## 6. 老存档迁移（按你的裁定）

```
age       = maxLifespan − lifespan          // 镜像等价，进度不丢
lifeRatio = clamp(maxLifespan / U_base(realm, lv), 0.9, 1)
lifeBonus = maxLifespan − lifeRatio × U_base(realm, lv)     // ≥ 0，吸收装备加成
deathLine = maxLifespan                     // 原值精确保留，老玩家不吃亏
```

- 落点：读档归一化 @249385。
- 该公式保证 `deathLine` **逐位等于**老存档的 `maxLifespan`（`lifeBonus` 吸收溢出部分），迁移前后进度完全一致。
- 迁移是一次性的：存档里一旦有 `age` 字段就跳过。

### 8.1 装备 `maxLifespanBonus` 是**死路径**（本轮查实，风险降级）

@309815 的 `sy()` 映射表里确实写了 `maxLifespanBonus:"maxLifespan"`，但：

- `maxLifespanBonus` 全 bundle **只出现 1 次**（就是这张映射表自己）
- **没有任何装备定义**含 `effects:{maxLifespanBonus:…}`（`effects:\{[^}]*[Ll]ifespan` 命中 0）
- 真正算装备加成的 `xs()`（@323384）用的映射表 `e4` **根本不含** `maxLifespanBonus`

⇒ 装备加寿从来没生效过，**不会污染隐藏死线**。本次只需把这张死映射表顺手删掉/改道，不需要担心存量数据。

### 8.2 丹药效果缩放（真实存在的边界）

@577963 `Ic()` 里 `permanentEffect` 会乘炼丹品质系数 `u = l×0.8` 再 `Math.floor`：

```js
d.maxLifespan!==void 0&&(d.maxLifespan=Math.floor(d.maxLifespan*u))
```

若 `maxLifespan` 数值很小（3/5/8），缩放后可能变成 2/4/6 甚至 **0**。重构时这条路径要一并核对，加最小保底（`Math.max(1, …)`），避免加寿被抹平。
