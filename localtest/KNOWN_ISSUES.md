## KI-001 · 存档灵石偶发归零（2000000 → 0）

| 项 | 内容 |
|---|---|
| **发现于** | 0.8.7 沙盒 E2E，断言 **E5-3** |
| **现象** | 某次存档读回 `spiritStones` 由 2,000,000 变为 0 |
| **是否 0.8.7 引入** | **否。0.8.6 历史既有**（0.8.6 基座同样可复现，非本批回归） |
| **阻塞等级** | 不阻塞 0.8.7 上线 |

### 证据（服务端 `srv/index_v28.ts`，指纹 `ad9ed2ff9880ef2280e9a37f0271a7ed`）

`POST /api/save` 有**三重保护**，服务端侧数学上不可能把字段压低到 0：

1. **单写者会话锁**（`:2073-2083`）：带 `X-YL-Session` 时校验 `active_sessions.session_id` 归属，不匹配 → `409 session_superseded`。头缺失放行（兼容老客户端/GM）。
2. **payload 结构守卫**（`:2091`）：`isValidSavePayload()` 在任何 DB 写之前拒绝畸形体（`{"logs":[]}` / `{"player":null}` / `{"player":[]}`），返回 `400 invalid_save`。此守卫正是 0.8.6 为「畸形体写坏账号」加的补丁。
3. **防倒滚**（`:2125-2131`）：`row && (!Number.isFinite(baseRev) || baseRev < curRev)` → `409 stale_save`，回传云端现档，**不写不记账**。仅 `row` 不存在（新号首存）才放行 INSERT。

此外 `settleSaveEconV2()`（`:1773`）**只钳正增量**（防刷经济），不会压低任何字段。

⇒ **归零只能来自客户端上传的 payload 本身**（即客户端在某个状态下把 `spiritStones` 算成了 0 并提交）。服务端「十环链」中所有 `UPDATE saves` 的计数恒等，无静默清零路径。

### 归因结论

客户端侧经济状态机在**特定操作序列**下可能算出 0（未定位到确切触发路径）。属**客户端历史设计债**，与 0.8.7 的 T1~T11 改造无因果关系。

### 处置

- 0.8.7 照常上线，**不阻塞**。
- 单独跟踪：需要复现出确切操作序列（建议加客户端经济流水埋点，或对 `/api/save` 增加「字段骤降告警」日志：当 `spiritStones` 相对上一版跌幅 > 90% 时打 warning 但放行，用于抓现场）。
- **不要**为了这条改服务端防倒滚逻辑——现有三重保护是对的，放宽反而会放大风险。

## KI-002 · `fun_daily` UNIQUE 带 `count` 导致「并发恰 1 次」语义不可保证

| 项 | 内容 |
|---|---|
| **发现于** | 0.8.7 沙盒 E2E，断言 **E9-8**（买诛妖符并发 6） |
| **现象** | 设计文档写「并发 6 恰 1 成功」，实测 `codes=[200,200,409,409,409,409]`（成功 2 次） |
| **是否缺陷** | **不是实现缺陷**，是**设计文档口径错** |
| **阻塞等级** | 不阻塞（已裁决，见下） |

### 证据

`fun_daily` 表：`UNIQUE (player_id, date, kind, count)`（`srv:790`；0.8.6 基座 `_chainstage/s05.fun086.ts:774` **逐字相同** ⇒ 历史既有）。
守卫逻辑：读 `used = COUNT(*)` → `INSERT ... count = used+1`。
⇒ 并发时两个请求都可能读到 `used=0`，分别插 `count=1` 和 `count=2`，**UNIQUE 不冲突**，双成功。

**但上界严格 = 日上限**：读 `used=2` 时必 409 ⇒ `count` 只能取 1/2 ⇒ 最多 2 行。且每次成功都真扣 price（三段式扣费 + 失败补偿删行）⇒ **非双花**，只是「同一日多买了 1 次」。

### 裁决（用户 2026-09-29 拍板）

**接受「成功数 ≤ 日上限」语义，改设计文档口径**（零代码改动、零风险、不动已冻结产物）。

已改：
- `docs/0.8.7-design/T5-限时活动.md:133` 验收要点 ②
- `docs/0.8.7-design/0.8.7-build-plan.md:253` E9 行

### 处置

- 断言已改为上界形式（E9-8：`n_ok >= 1 and n_ok <= 2 and set(codes) <= {200,409}`）。
- 若未来产品上要求「严格每日 1 次」：需把守卫改成 `UNIQUE(player_id, date, kind)`（去掉 `count`）并改 INSERT 为冲突即拒 —— 属**破坏性 schema 变更**，须独立批次评估。

## KI-003 · 掉玉挂点是 fire-and-forget，收获回执后玉异步到账

| 项 | 内容 |
|---|---|
| **发现于** | 0.8.7 全量 E2E（e2e-eng attempt1），断言 **E8-4 / E8-5** |
| **现象** | E8-4 `balance=0 want=5` FAIL；紧接的 E8-5 再读已是 5（`bal 0→5`）⇒ **玉延迟一拍到账** |
| **是否回归** | **否。测试竞态**（同产物同脚本：`--only` 定点跑绿、全量跑红） |
| **阻塞等级** | 不阻塞（测试侧已修） |

### 证据（`srv/index_v28.ts`，指纹 `ad9ed2ff9880ef2280e9a37f0271a7ed`）

三处掉玉挂点**全部未 `await`**（fire-and-forget）：

| 挂点 | 行号 | 形态 |
|---|---|---|
| 灵田收获（`farmHarvestOne`） | `:6178` | `if (gain.stones > 0) actDropTokens(userId, gain.stones, now).catch(...)` |
| 炼丹出炉化灵 | `:5890` | 同上 |
| 离线收益领取 | `:9620` | 同上 |

`actDropTokens()` 自身 `async`、内部 `await dbRun(...)` 正常提交，但**调用方不等待** ⇒ 主流程回执先返回、玉稍后落库。

`--only` 跑批负载低 → 读之前恰好落盘 → 绿；全量跑负载高 → 读在落盘前 → 假红。

### 归因结论

设计意图（`T5-限时活动.md:113` 验收要点 ①「灵田收获结算后 balance 增量 == floor(...)」）隐含同步可见性，实现选了异步。**功能上无丢失**（轮询可见），但客户端在收获后**立即**刷新灵玉阁可能读到旧值（窗口 ~ms 级）。

### 处置

- **测试侧已修**（2026-09-29，`e2e_087.py` E8-4 改有界轮询 ≤3s 等入账，E8-5 复用同一 `bal`）。零产物改动。
- **记录建议（不阻塞 0.8.7）**：后续批次可考虑把三处挂点改为 `await actDropTokens(...)`，让收获/炼丹/领取回执与玉入账**同事务可见**，消除客户端瞬时不一致窗口。代价：每路径多一次 DB 往返（~1ms）。**须独立批次**（改服务端 = 重建链 + 重算指纹 + 重跑全量）。
- 另注：`.catch(console.error)` 吞异常 ⇒ 若入账失败，玉**静默丢失且不重试**。属既有设计，一并留待上述后续批次评估。

## KI-004 · E17-2「旧 token 刷新后必 401」是**断言前提错误**（服务端无「重启失效会话」机制）

| 项 | 内容 |
|---|---|
| **发现于** | 0.8.7 E2E E17 收尾清号（idx=2），断言 **E17-2** |
| **现象** | `[FAIL] E17-2 旧会话 token 已失效（无残留会话） st=200`（期望 401） |
| **是否缺陷** | **不是实现缺陷**，是断言前提错误 |
| **阻塞等级** | 不阻塞（测试侧已修正） |

### 证据链（四环，任一环成立即证伪该断言）

1. **`authenticateToken`（`srv:1070-1089`）只校验 JWT 签名与有效期** —— 不查库、不校验用户是否存在。验签通过即 `next()`。
2. **`sandbox.sh:60` 的 `JWT_SECRET` 是固定字面量** `yl_local_sandbox_secret_2026` ⇒ `down → up` 不换签名密钥，旧 token 签名仍然有效。
3. **`seed.js` 复用同一批 user id**（`:98-104`：`SELECT id FROM users WHERE username=?`，已存在则只 `UPDATE users SET password_hash`），且 **`seed.js` 完全不碰 `active_sessions`**（grep 计数 = 0）。
4. **全库检索 `session_epoch` / `token_version` / `DELETE FROM active_sessions` —— 零命中**：服务端**根本没有「重启失效会话」这种机制**。

⇒ 刷新后旧 access token 依然合法，`GET /api/save` 返回 **200 是正确行为**（无状态 JWT）。E17-2 期望 401 在该设计下**永远不可能通过**。

### 真正的「顶号 / 无残留会话」机制（这才是该测的东西）

**`X-YL-Session` 单写者会话锁**（`srv:2022-2083`）：

| 端点 | 行为 |
|---|---|
| `POST /api/session/claim` | 生成新 `sessionId`，`INSERT OR REPLACE` 写入 `active_sessions`，返回 `{sessionId, superseded}` |
| `POST /api/session/heartbeat` | 带 `X-YL-Session`；不匹配 → **409 `session_superseded`**（`srv:2049-2050`） |
| `POST /api/save` | 带 `X-YL-Session`；不匹配 → **409 `session_superseded`**（`srv:2077-2078`）；**头缺失一律放行**（兼容老客户端/GM，`:2024`） |
| `GET /api/session/state` | 当前 `sessionId` + `active`（`last_seen` 60s 内） |

### 处置

- **测试侧已修正**（2026-09-29）：E17-2 拆为三条，改测真机制 ——
  - `E17-2` 刷新后旧 token 仍可鉴权（200，设计如此）
  - `E17-2b` 重新 claim 后，**旧 session_id 打 `/session/heartbeat` → 409 `session_superseded`**
  - `E17-2c` 旧 session_id 写档 `/api/save` → 409（并验证「会话校验先于 payload 校验」，`srv:2074` vs `:2091`）
- 零产物改动。E1~E16 结果不受影响（改动只在 `e17_cleanup()` 内）。

## KI-005 · E15-1「单次历练增量 P95<600」原测量**未隔离背景漂移**，不是有效仪器

| 项 | 内容 |
|---|---|
| **发现于** | 0.8.7 E2E E15（idx=4）→ 反向对照（idx=3） |
| **现象** | 改后 `P95=1060 mean=476.8 n=34` FAIL；改前 `P95=1291 mean=571.8 n=39` |
| **是否缺陷** | **不是产品缺陷**，是测试仪器缺陷（设计文档本身已预警） |
| **阻塞等级** | 不阻塞（仪器已按设计文档重做） |

### 为什么原指标无效（两步定性，第一步假设被数据证伪）

**第一步（假设，已证伪）**：怀疑非历练来源（离线结算/打坐/任务）污染信号。
**第二步（实测，成立）**：加了「阶段 A 背景漂移」后实测 **`E15-N2` P95=0 / mean=0.0**（历练关闭时灵石完全不涨）
⇒ 测量到的**就是纯历练收益**，**不是**背景污染。原假设作废。

**真正的根因是量纲错位**：

| | 口径 | 数值 |
|---|---|---|
| 设计文档 `:282` 要求 | 「**单次**灵石增量 P95 < 600」 | 阈值 **600/次** |
| 原实现测量 | 「每 **6.3 秒窗口**的 stones 增量」 | 改后窗口 P95=**681** |

产物里注明「**历练单次间隔 cooldown .5→3 秒**」⇒ 一个 6.3 秒窗口约含 **2 次**历练，
窗口值 ≈ 2× 单次值。**681 ÷ 2 ≈ 340 < 600** —— 断言一直在拿窗口值比单次阈值 ⇒ **假红**。

### 反向对照数据（改前/改后，同仪器同轮次）

| 口径 | 窗口 rawMean | 窗口 rawP95 | n |
|---|---|---|---|
| 改前 `index-v28-20260928.js` | 709.2 | 1462 | 29 |
| 改后 `index-v287-20260929.js` | 375.5 | 681 | 28 |

⚠️ **这个 1.89× 的幅度差不能归因给 T11**：两个 bundle 相差 **113,926 字节**（1,784,172 vs 1,898,098），
含 T1~T10 的**全部**改动，**不是单一变量对照**。故不能用它验证「×5 移除的收益降幅」。

**T11 生效的干净证据是另外两类**（单变量、可翻转）：

  `md:grid-cols-[minmax(...)]`），本子页的移动端堆叠可一次做对。

- item19 的包装器只做「剥 `[境界]` 前缀 → 重拼前缀」，**不动** `·融合` 后缀，故叠加行为与 item19 无关。
